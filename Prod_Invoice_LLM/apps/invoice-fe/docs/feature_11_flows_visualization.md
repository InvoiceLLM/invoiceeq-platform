# Feature 11: System Flow Visualization

Found already built and undocumented in the codebase (`app/flows/page.tsx`) — not created this session, no feature spec or tracker entry existed for it before now. This file backfills that gap so it's tracked like everything else, per the established convention.

**Important distinction:** this is a standalone, self-contained animated diagram — a teaching/demo tool, not a functional screen. It makes zero backend calls; every "live agent log" line is hardcoded simulated text (accurate to the real architecture — real function names, real Gap numbers — but not fetched from anywhere). It is **not** part of Service Flow's actual implementation, even though two of its four tabs visualize Service Flow's *design*.

### Theme & Styling Specifications
* Self-contained inline styles (not Tailwind), dark canvas gradient background, animated SVG node/edge diagram with per-flow accent colors (`#3B82F6` inbound, `#F59E0B` outbound/vendor, `#8B5CF6` chat).
* `isNew` nodes (Service Flow / Feature 6.1 additions) get an amber "NEW" badge — the page already self-discloses which nodes are spec-only vs. live, which is the right call and should be preserved in any future edit.

### Functionality
Four `FlowDef` constants (`INBOUND`, `OUTBOUND`, `CHAT`, `VENDOR_CHAT`), each a fixed list of nodes/edges/activity-log lines:
- **INBOUND** — the real, live extraction pipeline (upload → blob → OCR → classify → extract → verify → dedup → RAG index → COMPLETED/AUDIT_REQUIRED), annotated with real Gap numbers (15, 41, 42, 9, 55, 26/27).
- **OUTBOUND** — Service Flow's outbound pipeline exactly as designed in `feature_2.1_vendor_flow_ingestion.md`/`feature_7.1_vendor_flow_auditor.md` (parallel schema, imported OCR/verification, standing-rule mechanism, `NEEDS_REVIEW`). All nodes marked `isNew: true` — correctly reflects that none of this is built yet.
- **CHAT** — the real, live query agent (cache → history → rule injection → classify → SQL self-heal → synthesis), annotated with real Gap numbers (23, 48/52, 11, 20, 32, 34, 45).
- **VENDOR_CHAT** — Feature 6.1's direction-aware Chat design (dual-direction rule injection, `flow_direction` schema awareness, combined/net SQL). Marked `isNew: true` — correctly reflects spec-only status.

`FlowCanvas` renders the SVG node/edge graph with animated "packet" dots traveling along edges during playback. `AgentPanel` shows a per-node simulated terminal log, typed out line-by-line. Playback controls (play/pause/reset/speed) drive a `setTimeout`-chained sequence per flow.

### Explicitly out of scope / risk to flag
- Because two tabs visualize unbuilt Service Flow design as a polished, confident animation, there's a real risk of this page being mistaken for "it's built" by someone skimming quickly. The `isNew`/"NEW" badges and "spec only" text already mitigate this — any future edit to this page must preserve that distinction, not soften it.
- No live data anywhere on this page — if it's ever repurposed as an actual operational monitoring view, that would be a different feature entirely (and would want a very different implementation, reusing Gap 2/57's real log-line SSE events instead of hardcoded activity arrays).

- [x] **Task 11.3 / Gap 58: Canvas didn't auto-scroll to the active node during playback — Fixed 2026-07-27.** The `.flow-canvas-wrap` container (`maxHeight: calc(100vh - 160px)`, `overflowY: auto`) is much shorter than the full diagram (nodes run from `y=30` to `y=1110+` on Inbound), so once autoplay walked past the first 2-3 nodes the active node scrolled off-screen with nothing telling the viewer to scroll down — it just looked like the animation had stopped. Fixed by adding a `canvasWrapRef` + a `useEffect` keyed on `[activeNodeId, isPlaying]` in `FlowsPage` that calls `container.scrollTo({ top: node.y + NH/2 - container.clientHeight/2, behavior: "smooth" })`, using each node's already-known `x`/`y` coordinates directly rather than DOM measurement. Also resets scroll to top on `resetFlow()` (tab switch / replay) so a new playthrough doesn't start mid-scroll. Verified live via Playwright against the real dev server: `scrollTop` tracked the active node correctly through the full Inbound sequence (0 → 63 → 233 → 373 → 563 → 733 → 873px as playback progressed).
- [ ] **Task 11.4 / Gap 59: Outbound tab's autoplay silently freezes partway through — found 2026-07-27, not yet fixed.** `OUTBOUND`'s `sequence` array includes `{ nodeId: "ob_rules", edgeIds: [] }` as its 4th of 8 steps (not the last). `runStep()` treats `edgeIds.length === 0` as "flow finished" (`setIsPlaying(false)`) regardless of whether more steps remain in `sequence` — so autoplay stops right after the "OUTBOUND Global Rules" node (~15s in) and never automatically reaches LLM Extraction (Outbound) / Verification Suite / VERIFIED / RAG Indexing. Pressing Play again just replays `ob_rules` (since `stepIndex` never advanced past it), it doesn't resume forward. `INBOUND`'s equivalent branch node (`audit_req`) is correctly *excluded* from its `sequence` array, which is the right pattern — `OUTBOUND` should follow it (drop `ob_rules` from `sequence`, since `ob_ocr`'s own step already fires the `oe-rules-extract` edge that visually activates it). Confirmed live via Playwright against the real dev server: `isPlaying` flips to `false` at t≈15.5s with 4 of 8 nodes never played. `CHAT` and `VENDOR_CHAT` don't have this bug — only their terminal (last) node has empty `edgeIds`.
- [x] **Task 11.5 / Gap 60: Viewer had to manually scroll down after pressing Play — Fixed 2026-07-27.** The `.flow-canvas-wrap` container sits below the page's own ~230px sticky header/toolbar, so on a normal viewport its lower portion started below the fold even before playback began — Gap 58's *internal* auto-scroll had nothing to fix this since the container itself wasn't fully in view yet. Fixed by calling `canvasWrapRef.current?.scrollIntoView({ behavior: "smooth", block: "nearest" })` at the top of `handlePlay()`, so the whole container is brought into view the moment Play is pressed. `block: "nearest"` was chosen over `"start"` deliberately — it only scrolls as far as needed, keeping the Pause/Reset/speed toolbar visible instead of pushing it above the fold. Verified live: container bottom went from 869.5px (70px past an 800px viewport) to 799.5px (fully visible) within ~1.2s of clicking Play.
- [x] **Task 11.6 / Gap 61: No guidance telling a first-time visitor what to do — Fixed 2026-07-27.** The only instruction anywhere on the page was buried in `AgentPanel`'s empty state on the right ("Press Play to watch agents work / or click any node to inspect") — easy to miss, especially combined with Gap 60. Added a dismissible-by-progress hint banner directly under the flow tabs ("👆 Pick one of the 4 flows above, then press ▶ Play..."), shown whenever `!isPlaying && nodeStates` is empty for the current flow, so it naturally disappears once the visitor has actually played something and reappears if they switch to an unplayed tab. Verified live: present before Play, gone after.
- [x] **Task 11.7 / Gap 62: Page rendered inside the full authenticated app Shell (Sidebar + Header) — Fixed 2026-07-27.** `/flows` is a standalone, no-login public demo (confirmed: no `middleware.ts`, no Clerk/`useAuth` anywhere on this page or in the root layout) meant to give an anonymous visitor "a feel of the project" — but `app/layout.tsx` unconditionally wraps every route in `<Shell>`, which renders the same `Sidebar` (Dashboard/Ingest/Invoices/Chat/Settings/Help) used by the real, tenant-scoped app. A visitor with zero context could click any of those straight into real internal screens that mean nothing to them out of context. Fixed in `components/layout/Shell.tsx`: added a small `STANDALONE_ROUTES` allowlist (currently just `/flows`) checked via `usePathname()` — matching routes render full-bleed with no Sidebar/Header at all; every other route is completely unaffected. Verified live: `/flows` now has zero sidebar-like elements in the DOM, while `/dashboard` still renders its Sidebar normally.
- [x] **Task 11.8 / Gap 63: Auto-scroll (Gap 58) undershot on later nodes — the last 1-2 nodes of every flow never scrolled into view no matter how long autoplay ran — Fixed 2026-07-27, found while re-verifying Gap 58 live.** The Gap 58 fix computed the scroll target from each node's raw `x`/`y` viewBox coordinates, assuming 1 viewBox unit = 1 CSS pixel. But `FlowCanvas`'s `<svg>` is `width="100%"` with no explicit `height` (line ~548), so the browser auto-scales the rendered height to preserve the viewBox aspect ratio against whatever width it's stretched to — measured at ~1.9x on a 1400px-wide layout, not 1x. The raw-coordinate math undershot proportionally more the further down the flow it went, so by the last node the actual DOM position was ~1000px+ below where the fix thought it was — the Inbound "COMPLETED" box and the Chat "Response to User" box never scrolled into view, no matter how long you waited; a real user still had to drag the scrollbar manually to see them, exactly reproducing the original Gap 58 complaint for the tail end of every flow. Fixed by giving each node's `<g>` a `data-node-id` attribute and rewriting the scroll effect to read the node's *rendered* position via `getBoundingClientRect()` instead of its raw coordinates — immune to the SVG's scale factor (or any future layout change) since it measures real pixels. Verified live end-to-end: ran full Inbound (43s) and Chat (32s) autoplay to completion via Playwright; both flows' final node (`completed`, `q_resp`) confirmed `isFullyVisible: true` against the container's actual visible rect, with `scrollTop` landing exactly on `maxScroll` in both cases.

- [x] **Task 11.9 / Gap 64: No plain-language narration of the "story" for a non-technical viewer — Fixed 2026-07-27.** Everything on this page was either a technical node label (`OCR Engine`, `SQL Generation + Self-Heal`) or a technical activity log line in `AgentPanel` — nothing said, in plain words, "this is the user's action" vs. "this is the agent's reply." Added an optional `explainer?: string` field to `FlowNode`, set on just the human-facing nodes (upload/user-question nodes: "👤 User uploads..."/"👤 User asks a question..."; reply/outcome nodes: "🤖 Agent replies with a clear answer", "✅ Done — invoice fully processed", "⚠️ Flagged — a human needs to review this one") — deliberately *not* set on the internal technical nodes (OCR, classify, SQL generation, etc.), which already have the activity log for that detail. Rendered as a small blinking-dot bubble in the SVG directly above the node while it's active, using the same `blink` keyframe already used for the node state dot. Verified live: bubble appears exactly when its node becomes active and disappears once playback moves past it.

- [x] **Task 11.10 / Gap 65: Gap 61's hint banner was static text, easy to skim past without noticing — Fixed 2026-07-27.** Added a `hint-glow` box-shadow pulse to both the hint banner and the Play button itself (plus a blinking 👆 on the banner), so a first-time visitor's eye is drawn to the actual clickable target, not just a sentence describing it. First attempt animated the button via `transform:scale`, which visually pulsed fine but continuously resized the button's hit-box — concretely, it broke Playwright's element-stability check during verification (`click()` timed out waiting for the button to stop moving). Switched to a box-shadow-only pulse (same technique as the hint banner) which doesn't touch layout/size, fixing both the automation issue and, more importantly, a jumpier-than-necessary interaction target for real clicking too. Both animations stop once the current flow has been played once (same condition as Gap 61's banner).
