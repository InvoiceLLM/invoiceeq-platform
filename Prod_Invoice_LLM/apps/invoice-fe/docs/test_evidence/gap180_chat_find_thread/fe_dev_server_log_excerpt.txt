This is exactly the failure Gap 177's root-cause analysis predicted
(fe_features_tracker.md, "Root cause found 2026-08-10" by NEW_ISSUES_2026-08-10.md
N-07): lib/backendProxy.ts's proxyJson() always does
`const data = await response.text()` (empty string for a real 204 from
routers/chat.py's DELETE /chat/sessions/{id}) then constructs
`new NextResponse(data, {status: 204, ...})` — a null-body status
constructed with a non-null (if empty) body, which the Fetch spec forbids.
Confirmed live in this exact stack, not just in isolation.

committed the delete despite the 500 returned to the browser:

Row is gone server-side. The FE's local `sessions` state array is never
updated (`useChatSession.ts::deleteSession()`'s catch block only sets an
error string, never filters `sessions`), so the thread keeps rendering in
the sidebar — and keeps matching the search filter — until a full page
reload re-fetches the real (now-shorter) session list from the backend.
