- `[~]` **Gap 12: Clerk cross-app session handshake never completes on the Azure dev deployment — `azurecontainerapps.io` is a Public Suffix List domain** — found 2026-07-31 testing the deployed FE at `ca-invoice-fe-dev...azurecontainerapps.io`. Symptom: `?__clerk_handshake=<jwt>` stays stuck in the URL / dashboard never loads. Root-caused by decoding the actual handshake JWT payload (not a guess): Clerk is issuing `Set-Cookie: __client_uat=0; Domain=azurecontainerapps.io; ...` — attempting to scope the session cookie to the **shared parent domain across every Azure Container Apps customer** so `invoice-website` and `invoice-fe` (different subdomains) can share one login session. `azurecontainerapps.io` is a Microsoft-registered shared-hosting suffix, almost certainly on browsers' Public Suffix List for exactly this reason (same category as `azurewebsites.net`) — browsers silently reject any `Set-Cookie` targeting a public-suffix domain, so the cookie never persists, Clerk's middleware sees no session on the next request, and the handshake loops indefinitely. **Not a CORS issue** (this is a top-level navigation redirect, not a fetch/XHR call — `ALLOWED_ORIGINS` is unrelated) and **not reproducible locally** (`localhost` isn't a public suffix, and cookies aren't port-scoped, so `localhost:3000`/`localhost:3001` share sessions fine — confirmed during Gap 9 testing).
  - **Real fix**: a custom domain for `invoice-website`/`invoice-fe` (e.g. both under `*.yourinvoiceai.com`), configured in the Clerk Dashboard, so Clerk can scope the cookie to a domain that's genuinely this tenant's own — not a public suffix.

- `[ ]` **Gap 11: No standalone (no-company) signup — confirmed by design, not a bug, but worth a deliberate decision** — found 2026-07-30 while reviewing the signup flow. Verified in code: `SignupPage::handleSignup` requires `orgName` (a `required` form field) and always calls `window.Clerk.createOrganization()`; backend `POST /auth/provision` (`routers/auth.py::provision_tenant`) requires `clerk_org_id` as a non-optional field and has no code path for a user without one. Every provisioned user becomes `role="Admin"` of a new/existing `Tenant`. Additional users only ever join an *existing* tenant via the admin-only `app/admin/page.tsx` → `/api/admin/create-user` (Gap 10) — there is no self-service "just sign up as me, no company" path anywhere.
  - **What would actually break if a standalone user existed today**: everything in the backend schema is `tenant_id`-scoped — `Invoice`, `TenantConnection`, `ExtractionTemplate`, `User` all key off it; blob storage paths are literally `tenants/{tenant_id}/{direction}/{batch_id}/{filename}` (`queue_worker/handlers.py`); `get_tenant_context()` resolves `tenant_id` from the JWT's org claim with no fallback for "authenticated user, no org." A user with no Clerk Organization has no `org_id` claim at all, so a PDF they uploaded would have nowhere valid to be scoped/stored under the current model — not "it stores insecurely," but "the upload path has no tenant_id to build a blob path or DB row with" at all.
  - **Recommended fix, if this is wanted (not built)**: don't rip out `tenant_id` scoping — auto-provision an invisible one-person `Tenant` for a standalone signup instead (e.g. named from the user's email, `billing_plan="free"` exactly like today). This needs zero schema or storage changes since a "standalone user" would just become a `Tenant` of one; the only change is the signup FE no longer *requiring* an org name from the user, generating one instead. A deeper alternative (make `tenant_id` nullable everywhere and add a parallel `user_id`-scoped storage/query path) would touch nearly every table and query in the codebase for no real benefit over the auto-provisioned-tenant approach, so not recommended.
