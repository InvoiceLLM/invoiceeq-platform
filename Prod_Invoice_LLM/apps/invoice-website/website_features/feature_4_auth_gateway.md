# Feature Website 4: Clerk Auth Gateway & Company Provisioning

Manage organisation sign-up, Clerk-based authentication, role-scoped login, and redirect users to the `invoice-fe` dashboard.

**Implementation note (2026-07-28):** built via Clerk **Organizations** (one Clerk org per tenant, explicitly created at signup) rather than the domain-auto-detection flow originally spec'd below in Tasks 4.1-4.3 — email-domain matching is kept only as a legacy fallback for tenants that predate Clerk. Reconciled from the `auth-feature-4` branch onto current master; see `website_features_tracker.md` Gap 2/4/9/10 for what's still open (real Clerk keys, auth enforcement, the real-key verification run, admin route auth).

**Further cherry-pick (2026-07-30):** forgot-password, an admin console, and the Docker/infra to actually deploy `invoice-website` were pulled from the same `auth-feature-4` branch (see Functionality items 6-7 below and `website_features_tracker.md` Gaps 3/5/6/7/8). Scratch/session docs from that branch (fix summaries, troubleshooting notes, duplicate implementation-plan docs) were deliberately left out — their real content was mined into this doc and the tracker instead.

### Functionality
1. **Signup** (`SignupPage`/`handleSignup`): admin fills org name/type/country + email/password → `signUp.create()` → Clerk session activated → `window.Clerk.createOrganization()` creates the Clerk org → org metadata (`orgId`, `orgName`, `orgType`, `country`, `role: "admin"`) written to the user → backend `POST /auth/provision` called to create the matching `Tenant` row (`clerk_org_id` linked) → redirect to `/login`. `unsafeMetadata.role` is written for historical/display reasons only (Gap 173 below) — it grants nothing.
   - **Provisioning is no longer best-effort, 2026-08-11 (BE Gap 133 / website Gap 176).** Org creation and the provision call used to be `console.warn`-and-continue, and the flow redirected to `/login` either way. That was the single largest contributor to Gap 133: a user whose organisation never reached the backend arrived at a working-looking app whose data lived in an unrelated tenant (or nowhere), with nothing on screen ever saying so. Both failures now **stop the flow on the signup page**. A failed provision shows *"Your account was created, but we couldn't finish setting up your organisation ({detail}). Click Retry — if it keeps failing, contact support and quote org id {orgId}."* with a **Retry** button (`handleRetryProvision`) that re-POSTs **only** the backend call — the Clerk user, the organisation and the active session all already exist by then, so re-running signup would just fail on a duplicate email, and `/auth/provision` is idempotent on `clerk_org_id`. A failed `createOrganization()` (or one returning no id) is terminal with a support-facing message and no Retry, since retrying it would risk creating duplicate orgs. The Clerk user id is read defensively (`result.createdUserId || window.Clerk?.user?.id`) — it being null used to skip the provision call silently. The `unsafeMetadata` write stays non-blocking: it is display-only now that the app renders the backend's resolved tenant name (see Functionality item 3).
   - **The provision request is authenticated, same change.** `provisionTenant()` mints `getToken({ template: "invoice-app" })` from the live Clerk client immediately after `setActive` and sends it as a bearer token. Client-side rather than server-side because the session cookie the proxy's `auth()` reads can lag a just-completed `setActive` (proven live in Gap 157), and signup is exactly when that lag is worst; the proxy still falls back to minting server-side if no header arrives.
   - **Email verification (OTP) handling added, 2026-08-18 (Gap 182).** `signUp.create()` can return `status: "missing_requirements"` when Clerk requires email verification before the account is usable; the pre-fix code had no branch for this at all and fell into a dead-end message ("check Clerk dashboard settings..."), leaving the Clerk user stuck half-created — a same-email retry would then fail as "already taken," which is what Gap 182 originally reported. The page now calls `prepareEmailAddressVerification({ strategy: "email_code" })` and renders an OTP input pane on this status; `handleVerifyEmail` completes it via `attemptEmailAddressVerification` and reuses the same `completeSignupAndProvision()` path (org creation → `setActive` → `provisionTenant`) as the direct-complete case, preserving the Gap 133 blocking-error semantics above verbatim. **Closed without a live repro against this Clerk instance** — flagging honestly, per this repo's history of premature-closure audits: it's unconfirmed whether email verification is even turned on here (Gap 9's 2026-08-03 closing note recorded a successful real-key signup with no `missing_requirements` handling present, which cuts against it). **Known gap**: "← Back to Sign Up" clears local state but not the pending Clerk attempt, so a same-email resubmit after going back can still fail as "already taken" — a residual version of the original symptom. See `website_features_tracker.md` Gap 182 for full verification status.
2. **Login** (`LoginPage`/`processSignIn`): plain email/password sign-in via `signIn.create()`, no role picker. Supports email-code second-factor (OTP) if Clerk requires it. After sign-in, activates the Clerk organization membership (`unsafeMetadata.orgId` if present, else the sole `organizationMemberships` entry) and redirects to `invoice-fe` (`${NEXT_PUBLIC_FE_URL}/dashboard` for everyone today — `invoice-fe` has no separate admin route yet; which screens/tabs actually render there is resolved entirely post-login from the backend's `GET /auth/me`, independent of anything on this page).
   - **Role picker and Access Denied gate removed, 2026-08-07 (Gap 173).** The login card used to show an "I am signing in as" Admin/User toggle and deny sign-in with an Access Denied state if the selected role didn't appear in the user's `unsafeMetadata.role` string. That field is client-writable via `Clerk.user.update()` from a browser console with no backend involved — the gate was cosmetic at best (Sidebar.tsx already filters real screens from the backend-resolved role regardless of what was picked here) and, worse, `dependencies.py` used to also read this same field to decide real backend permissions, meaning a user could self-grant Admin the same way. The backend fix (below) now trusts only Clerk's own `org_role`; this page's picker/gate were removed as the same fix's FE half, not a separate cosmetic cleanup.
   - **OTP "← Back to Login" fixed, 2026-08-18 (Gap 177).** The button used to only flip local component state, leaving Clerk's `signIn` instance stuck in `needs_second_factor` — a background token re-evaluation would then bounce the view back into OTP mode a couple seconds later, trapping the user. Fix: the handler now also calls `signOut()` (via `useClerk()`) to actually clear the pending sign-in attempt. Live-tested and confirmed working.
   - **Card structure simplified in the same change.** The 2026-08-05 two-tab mode switcher (Gap 164: **"Sign In"** / **"+ Create Organisation"** tabs, `S.tabRow`/`tabBtnStyle`) is gone too — with the role picker removed, "Sign In" was the only thing left to switch to, so the tab row no longer earned its place. "+ Create Organisation" used to switch to an intermediate static pane (`S.createPane`: icon, "Set up your workspace" heading, copy, a second `Create Organisation →` button linking to `/signup`) — that extra click is gone; the header's own **"+ Create Organisation"** entry point now links straight to `/signup`. Final shape: header ("Welcome back" / "Sign in to your workspace") → credentials form (or OTP form) directly, no tabs above it → a small **"New here? Create an organisation →"** link below the submit button, linking to `/signup`. `S.createPane`/`createIcon`/`createTitle`/`createCopy`/`createBtn`/`roleRow`/`roleIcon`/`accessDenied` styles and the `roleBtnStyle`/`tabBtnStyle` helpers were removed along with the elements that used them.
3. **Backend provisioning** (`POST /auth/provision`): idempotent — repeat calls with the same `clerk_org_id` return the existing tenant rather than duplicating. Falls back to linking an existing domain-matched tenant (pre-Clerk-org tenants) before creating a new one.
   - **Authenticated, and three defects fixed, 2026-08-11 (BE Gap 133).** (a) The endpoint took **no auth dependency at all**; an anonymous POST could rename and claim an existing tenant (reproduced over HTTP: an anonymous request renamed a seeded populated tenant to the caller's org name and attached the caller's `clerk_org_id`, returning 200). It now verifies a real Clerk token and **403**s unless the token's `sub` equals `clerk_user_id` in the body; the proxy route (`app/api/auth/provision/route.ts`) forwards the caller's `Authorization` header, falls back to a server-side `auth()` + `getToken({ template: "invoice-app" })`, refuses with 401 if neither yields a token, and `console.error`s the backend status/body server-side. (b) **Domain adoption no longer takes over a populated tenant** — it requires the domain-matched tenant to have no `clerk_org_id` *and* no users; the org-less, user-less case (the pre-Clerk-org tenants this branch exists for) still links as before. (c) `Tenant.domain` is unique, so the **second** organisation signing up from any shared email domain used to raise `IntegrityError` as a bare **500**, leaving a Clerk user with no tenant; the insert now retries once with `org-<clerk_org_id>.invalid` and returns an explicit 409 only if that also conflicts.
4. **JWT tenant resolution** (`get_tenant_context`): every authenticated backend request decodes the Clerk session JWT and resolves `clerk_org_id`/`tenant_id` claims to a `Tenant` row (priority: `clerk_org_id` → `tenant_id` claim), backfilling `clerk_org_id` onto tenants found via the older lookup path. Falls back to `MOCK_TENANT_ID` when no `Authorization` header is present (local dev only — `ALLOW_MOCK_AUTH`, default off).
   - **The email-domain fallback is gone, 2026-08-11 (BE Gap 133).** Priority 3 used to look a tenant up by the email domain and, failing that, create one. Because a missing `email` claim produces the placeholder `user_<clerkid>@domain.com`, every affected user shared the domain `domain.com` and they were merged into one unrelated tenant. For a real token, a `clerk_org_id`/`tenant_id` that resolves nothing is now a **`409`** naming the org id — the app refuses rather than guessing which workspace someone belongs to. Consequence, accepted deliberately: an account whose organisation was never provisioned cannot sign in until it is (the signup flow's Retry above is the remedy).
5. **Sign-out** (`invoice-fe` `Header.tsx`): calls the backend `POST /auth/logout` (via `invoice-fe`'s own `/api/auth/logout` proxy route) for server-side cleanup, then Clerk's `signOut()`, then redirects to `${NEXT_PUBLIC_WEBSITE_URL}/login`.
6. **Forgot password** (`ForgotPasswordPage`): two-step Clerk reset — `signIn.create({strategy: "reset_password_email_code"})` sends a code to the user's email, then `signIn.attemptFirstFactor()` verifies the code and sets a new password in the same call. Matches the login/signup page's visual design.
   - **Autofill targeting, fixed 2026-08-05 (Gap 161).** None of this form's three inputs originally carried a `name` or `autoComplete` attribute, so browsers fell back to positional heuristics: in the `verify` step the reset-code input is the *first* text input in the form, which Chrome read as the identifier field and filled with the user's saved email address. Each input now declares its purpose explicitly — email: `name="email"` / `autoComplete="email"` / `inputMode="email"`; reset code: `name="reset-code"` / `autoComplete="one-time-code"` / `inputMode="numeric"`; new password: `name="new-password"` / `autoComplete="new-password"` (which also stops password managers offering the *old* password here). Attributes confirmed present in the rendered DOM.
7. **Admin console** (`app/admin/page.tsx` + `CreateUserModal`): lists the current org's members and lets an admin create a new user directly (name/email/password → `POST /api/admin/create-user`). That route calls Clerk's REST API directly (bypassing the SDK to avoid a version-compatibility issue with email verification), creates the user with `unsafe_metadata: {role: "member"}`, and immediately marks their email verified so they can sign in right away without a confirmation step. **Fixed 2026-08-07 (Gap 173)**: the route now also adds the new user to the caller's own Clerk Organization as `org:member` (via `orgId` from the caller's own `auth()` session) — previously it never did, so every Settings-added user had no real `org_role` at all and the backend had no choice but to fall back to the client-writable `unsafe_metadata.role` for them. `org_role` is now universal, not just for org founders. The route's own auth check is separate from this and was already fine.
8. **Password Visibility Show/Hide Toggle (Gap 353 / W-07 — Built 2026-09-02)**:
   - Interactive eye icon button (Lucide `Eye` / `EyeOff`) positioned inline within the right padding of password inputs in `app/login/page.tsx`, `app/signup/page.tsx` (both Password and Confirm fields), and `app/forgot-password/page.tsx`.
   - Toggles input type dynamically between `type="password"` and `type="text"`.
   - Accessible keyboard navigation (`tabIndex={0}`) and `aria-label="Show password"` / `aria-label="Hide password"`. Verified: `npx tsc --noEmit` and `npm run build` both clean.

**By design, not yet built: no standalone (no-company) signup exists.** Every account is created either as an org-founding Admin (Signup, step 1 above) or invited into an existing org by that Admin (step 7) — there is no path for a user to sign up without a company attached. See `website_features_tracker.md` Gap 11 for the full architectural analysis of what would need to change (short version: `tenant_id` scoping is load-bearing everywhere, including PDF blob storage paths — the clean fix is auto-provisioning an invisible one-person tenant, not removing tenant scoping).
