# Feature Website 4: Clerk Auth Gateway & Company Provisioning

Manage organisation sign-up, Clerk-based authentication, role-scoped login, and redirect users to the `invoice-fe` dashboard.

**Implementation note (2026-07-28):** built via Clerk **Organizations** (one Clerk org per tenant, explicitly created at signup) rather than the domain-auto-detection flow originally spec'd below in Tasks 4.1-4.3 — email-domain matching is kept only as a legacy fallback for tenants that predate Clerk. Reconciled from the `auth-feature-4` branch onto current master; see `website_features_tracker.md` Gap 2/4/9/10 for what's still open (real Clerk keys, auth enforcement, the real-key verification run, admin route auth).

**Further cherry-pick (2026-07-30):** forgot-password, an admin console, and the Docker/infra to actually deploy `invoice-website` were pulled from the same `auth-feature-4` branch (see Functionality items 6-7 below and `website_features_tracker.md` Gaps 3/5/6/7/8). Scratch/session docs from that branch (fix summaries, troubleshooting notes, duplicate implementation-plan docs) were deliberately left out — their real content was mined into this doc and the tracker instead.

### Functionality
1. **Signup** (`SignupPage`/`handleSignup`): admin fills org name/type/country + email/password → `signUp.create()` → Clerk session activated → `window.Clerk.createOrganization()` creates the Clerk org → org metadata (`orgId`, `orgName`, `orgType`, `country`, `role: "admin,user"`) written to the user → backend `POST /auth/provision` called to create the matching `Tenant` row (`clerk_org_id` linked) → redirect to `/login`. Org creation and the provision call are both best-effort/non-fatal — a failure there doesn't block the Clerk account itself from existing.
2. **Login** (`LoginPage`/`processSignIn`): user picks a role (Admin/User) then signs in via `signIn.create()`. Supports email-code second-factor (OTP) if Clerk requires it. After sign-in, checks the user's `unsafeMetadata.role` (comma-separated, e.g. `"admin,user"`) against the selected role — mismatch shows an Access Denied state rather than silently logging in as the wrong role. Resolves and activates the Clerk organization membership, then redirects to `invoice-fe` (`${NEXT_PUBLIC_FE_URL}/dashboard` for both roles today — `invoice-fe` has no separate admin route yet).
   - **Card structure, rebuilt 2026-08-05 around a two-tab mode switcher (Gap 164, which also closes Gaps 160 and 162).** A `mode` state (`"signin" | "create"`) drives what renders below the card header. The header itself is now generic — avatar icon, **"Get started"**, *"Sign in, or create your organisation"* — and is followed immediately by a 2-tab row (`S.tabRow` + `tabBtnStyle(active, color)`, `role="tablist"`/`role="tab"`/`aria-selected`): **"Sign In"** in the existing blue (`T.blue`) and **"+ Create Organisation"** in the existing green (`T.green`, the app's secondary-CTA convention). `signin` is the default.
   - `mode === "signin"` renders the pre-existing flow completely unchanged: the "I am signing in as" Admin/User role toggle, the credentials form (or the OTP second-factor form when `needsOtp`), the forgot-password link, error/access-denied boxes and the `→ Sign In as {role}` submit button.
   - `mode === "create"` renders a short static pane (`S.createPane`): a 🏢 icon tile, an **"Set up your workspace"** heading, one line of copy — **"Any name works, even a test one — takes under a minute."** — and a single green `Create Organisation →` button linking to `/signup`. Deliberately no inline org-creation form; the real fields already live on the signup page.
   - **Why a tab switcher rather than a compacted card**: the previous layout put the only real onboarding path — a small `S.signupRow`/`S.signupLink` "Create your organisation →" link — 6th in reading order, below a "New to InvoiceAI?" divider, inside a card with no `max-height`/`overflow`. On a ~700px-tall viewport at 100% zoom that link fell past the visible edge (Gap 160), which made the one available way to get an account invisible, and left the prominent Admin/User toggle implying two equally-available self-serve entry points when only the Admin/org-founding one exists (Gap 162). Promoting "+ Create Organisation" to a tab directly under the header removes the dependence on total card height entirely, and the pane's copy states the fact that was actually missing — a placeholder/test org name is fine. Both the divider row and the old signup link were removed along with their now-unused `S.dividerRow`/`S.dividerLine`/`S.dividerText`/`S.signupRow`/`S.signupLink` style entries.
   - Verified in a headless Chrome run at 1440×700: the tab row renders at y≈274 (well above the fold) with `Sign In` `aria-selected="true"` on load, the sign-in card measures 692px and its submit button is fully visible, and the create pane measures 551px with its `/signup` button visible without scrolling.
3. **Backend provisioning** (`POST /auth/provision`): idempotent — repeat calls with the same `clerk_org_id` return the existing tenant rather than duplicating. Falls back to linking an existing domain-matched tenant (pre-Clerk-org tenants) before creating a new one.
4. **JWT tenant resolution** (`get_tenant_context`): every authenticated backend request decodes the Clerk session JWT, resolves `clerk_org_id`/`tenant_id` claims to a `Tenant` row (priority: `clerk_org_id` → `tenant_id` → email domain), and backfills `clerk_org_id` onto tenants found via the older lookup paths. Falls back to `MOCK_TENANT_ID` when no `Authorization` header is present (local dev / no-auth-yet callers).
5. **Sign-out** (`invoice-fe` `Header.tsx`): calls the backend `POST /auth/logout` (via `invoice-fe`'s own `/api/auth/logout` proxy route) for server-side cleanup, then Clerk's `signOut()`, then redirects to `${NEXT_PUBLIC_WEBSITE_URL}/login`.
6. **Forgot password** (`ForgotPasswordPage`): two-step Clerk reset — `signIn.create({strategy: "reset_password_email_code"})` sends a code to the user's email, then `signIn.attemptFirstFactor()` verifies the code and sets a new password in the same call. Matches the login/signup page's visual design.
   - **Autofill targeting, fixed 2026-08-05 (Gap 161).** None of this form's three inputs originally carried a `name` or `autoComplete` attribute, so browsers fell back to positional heuristics: in the `verify` step the reset-code input is the *first* text input in the form, which Chrome read as the identifier field and filled with the user's saved email address. Each input now declares its purpose explicitly — email: `name="email"` / `autoComplete="email"` / `inputMode="email"`; reset code: `name="reset-code"` / `autoComplete="one-time-code"` / `inputMode="numeric"`; new password: `name="new-password"` / `autoComplete="new-password"` (which also stops password managers offering the *old* password here). Attributes confirmed present in the rendered DOM.
   - Note, not changed: `app/login/page.tsx`'s own email/password/OTP inputs still carry no `autoComplete` attributes. Its OTP field is not reachable by the same first-text-input heuristic (it only renders after a successful `signIn.create()` replaces the credentials form), so it wasn't reported and was left out of Gap 161's scope — worth a follow-up if login autofill is ever reported misbehaving.
7. **Admin console** (`app/admin/page.tsx` + `CreateUserModal`): lists the current org's members and lets an admin create a new user directly (name/email/password → `POST /api/admin/create-user`). That route calls Clerk's REST API directly (bypassing the SDK to avoid a version-compatibility issue with email verification), creates the user with `unsafe_metadata: {role: "user"}`, and immediately marks their email verified so they can sign in right away without a confirmation step. **Security gap, not yet closed**: the route has no server-side check on who's allowed to call it — see `website_features_tracker.md` Gap 10.

**By design, not yet built: no standalone (no-company) signup exists.** Every account is created either as an org-founding Admin (Signup, step 1 above) or invited into an existing org by that Admin (step 7) — there is no path for a user to sign up without a company attached. See `website_features_tracker.md` Gap 11 for the full architectural analysis of what would need to change (short version: `tenant_id` scoping is load-bearing everywhere, including PDF blob storage paths — the clean fix is auto-provisioning an invisible one-person tenant, not removing tenant scoping).
