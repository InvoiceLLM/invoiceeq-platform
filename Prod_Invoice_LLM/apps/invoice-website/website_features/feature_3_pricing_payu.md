New proxy route `app/api/billing/create-checkout-session/route.ts` (same shape as the existing `/api/auth/provision` proxy) — requires a real signed-in Clerk session (`auth()`), forwards the caller's token to the backend so `routers/billing.py`'s Admin-role gate can verify it, then relays the hash-signed field set back to the browser. `PricingTable.tsx` builds a hidden form from those fields and submits it — confirmed via Playwright that a signed-out click correctly redirects to `/signup?plan=pro`/`/signup?plan=pro_combined` first (checkout requires an authenticated Admin tenant context, so an anonymous visitor has to create an account before paying — same pattern as this site's existing "Get Started Free" CTA).
- [x] **Task 3.3: Implement PayU Success/Failure Result Pages** — **Corrected and actually built 2026-08-02.** This task was previously marked done on the claim that "no additional website-side work [is] needed; PayU never lands on `invoice-website` directly." That was **wrong on both counts**, and the consequence was live: `routers/billing.py` redirects the paying user to `{FRONTEND_URL}/billing/success?plan=…` / `/billing/failed`, and **neither route existed in either app** — a user who had just paid real money got a 404. Now built, in `invoice-website`:
  * `app/billing/success/page.tsx` — reads `?plan=` (keys mirror `billing.py::PLAN_AMOUNTS`: `pro`, `pro_combined`) and `?txnid=`, names the plan and price in human terms, and links onward into the app. **Makes no API call**: `_handle_payu_callback()` has already committed `tenant.billing_plan` before redirecting here, so a fetch would add nothing and could fail in a way that made a successful payment look failed.
  * `app/billing/failed/page.tsx` — handles the query params the backend *actually* emits, in three severities: a plain decline (`?txnid=`, no reason) is safe to retry; `malformed`/`hash_mismatch`/`unverifiable` mean *we could not verify*, not that the money stayed put; `unknown_plan`/`unknown_tenant` mean the payment demonstrably **succeeded** at PayU and we failed to apply it. The latter two groups get a "contact support with this reference" path and **no retry CTA** — offering "try again" there would invite a second charge. `txnid` is surfaced whenever present.
  * Both pages are **public**, deliberately not behind Clerk: a user returning from PayU may land in a tab with no live session. Both match Feature 1's marketing shell (`Header`, `glass-card-enterprise`, `btn-primary-gradient`/`btn-secondary-glass`, `animated-hero-heading`, `#22D3EE`/`#94A3B8`/`#222D3D` tokens) and reuse the global `Footer` from `app/layout.tsx`.
  * Why these live here and not in `invoice-fe`: post-Multi-Zone-proxy (tracker Gap 12) invoice-fe is `ingress.external: false`, so a browser returning from a third party physically cannot reach an invoice-fe URL. `invoice-website` is the only public origin, `next.config.js`'s `fePages` list deliberately excludes `billing` (no collision), and this app already owns the other half of the flow.
- [x] **Task 3.5: Public pass-through for PayU's `surl`/`furl`** — Added 2026-08-02 (new task; the original spec assumed PayU could reach the backend). `invoice-be`'s ingress is internal-only, so PayU could never POST the callback to it in Azure. `app/api/v1/billing/payu/{success,failure}/route.ts` + `relay.ts` mirror the backend's path exactly, so `billing.py` needed no URL-shape change — only `BACKEND_PUBLIC_URL`'s value changed, to invoice-website's origin. The relay is **unauthenticated on purpose** (PayU has no session; copying `create-checkout-session`'s `auth()` gate would break the callback — and security is unaffected, since the backend verifies PayU's response hash *and* runs an independent `verify_payment` cross-check before trusting anything), forwards method/`Content-Type`/raw body verbatim, and uses `redirect: "manual"` to **relay** the backend's 303 rather than follow it — the same mistake already made and fixed on the connectors OAuth callback (`fe_features_tracker.md` Gap 98 follow-up). If the backend is unreachable it redirects to `/billing/failed?reason=unverifiable&txnid=…` rather than 500-ing at a user who may have just paid.
