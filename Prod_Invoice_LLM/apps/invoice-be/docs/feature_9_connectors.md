### Functionality
`get_connectors_status()` reads the tenant's `TenantConnection` rows and reports `Active`/`Inactive`/`Not Configured` per provider. **The OAuth app itself is one shared, company-owned app per provider (`GOOGLE_CLIENT_ID`/`SECRET`, ~~`SALESFORCE_CLIENT_ID`/`SECRET`~~ env vars) — not per-tenant.** Each end-user connects *their own* Drive account through it; the resulting per-tenant token is what `TenantConnection` stores.

`get_auth_url()` / `oauth_callback()` (`_has_real_credentials()` gate, added 2026-07-30): once a provider's real Client ID is configured (Google is, as of this date, using the dev's personal GCP OAuth app standing in for the company app pending a dedicated one), the redirect URL is real and `oauth_callback()` makes a real `POST` to that provider's token endpoint (`GOOGLE_TOKEN_URL`~~/`SALESFORCE_TOKEN_URL`~~) to exchange the code for a real access/refresh token. Google requests are sent with `access_type=offline&prompt=consent` so a `refresh_token` is always returned (needed for the "connect once" experience — `TenantConnection.encrypted_refresh_token` already existed but nothing wrote a real value into it before this). A provider with no real Client ID configured yet ~~(Salesforce, as of this date — still consumer-key placeholders)~~ transparently falls back to the previous simulated exchange so local/dev testing keeps working without a registered app.

**Real file listing/download (Gap 98, 2026-07-30):** `list_connector_files()` and `handle_import_connector_file()` now call the real Google Drive API (`utils/connector_files.py`) whenever an active connection exists for a provider with `has_real_credentials()` true — real `files.list` (folder-scoped query, PDFs + folders only) for browsing, real `alt=media` download for import. `utils/connector_oauth.py::get_valid_access_token()` transparently refreshes an expired access token via the stored `refresh_token` before either call, and persists the renewed token/expiry — this is what makes "connect once" actually mean "never ask again," not just a schema field with nothing reading/writing it. Verified against the live Drive API with a deliberately invalid token (real `401` back, confirming the request shape and that the Client ID/Secret are genuinely registered with Google) since a full real-token test requires an interactive browser consent step. Falls back to the previous mock file list/stub bytes when no active real connection exists, or for a provider without real credentials.

**Autopilot sync history is a list of RUNS, not a list of files (Gap 427, 2026-09-04).** Feature 13's `services/autopilot_sync.py::run_sync()` had always minted a per-run `batch_id` and stamped it on the `Invoice` rows it created — but never on its own `TenantAutopilotLog` rows. `GET /autopilot/history` therefore had no notion of a run at all and could only page over individual files, which is what made the FE Sync History table an unreadable wall of raw Google Drive file IDs with no batch summary. Three changes make a run a first-class thing:

1. **`TenantAutopilotLog` gained `batch_id`, `trigger` and `source_file_name`** (all nullable; migration `a1b2c3d4e5f7`, plus index `idx_autopilot_log_tenant_batch` on `(tenant_id, batch_id)` — neither existing index serves a GROUP BY read path). Nullable *permanently*, not just for the migration window: the run a pre-existing row belonged to was never recorded anywhere and Drive file names are not recoverable from a `fileId` alone, so there is nothing to back-fill from.
2. **`run_sync()` takes a `trigger` kwarg** (`'scheduled'` default; `routers/autopilot.py::trigger_sync()` passes `'manual'`, `run_sync_for_all_due_tenants()` passes `'scheduled'` explicitly) and threads `batch_id`/`trigger`/`file_name` into **every** `_write_log()` call — SUCCESS, SKIPPED_DUPLICATE and both FAILED paths. A run that finds nothing new writes **one `NO_NEW_FILES` marker row** with an empty `source_file_id`, so an empty run is still visible instead of leaving no trace. `NO_NEW_FILES` is deliberately not `SUCCESS`: both dedup layers and the incremental `since_dt` lookup filter on `status == 'SUCCESS'`, and a marker row carrying an empty file id/hash must not participate in any of them.
3. **`GET /autopilot/history` returns runs** — a single `GROUP BY batch_id` (tenant-scoped, `min`/`max(ingested_at)` for `started_at`/`finished_at`, `SUM(CASE ...)` per status), ordered by `started_at` desc. This is a **breaking response-shape change**; the FE is rewritten against it in parallel (FE Gap 428).

```
GET /autopilot/history?page=&page_size=  -> {
  items: [{ batch_id: str|null, trigger: str|null, source_type: str,
            started_at: iso, finished_at: iso,
            files_seen: int, imported: int, skipped: int, failed: int,
            status: "SUCCESS"|"PARTIAL"|"FAILED"|"NO_NEW_FILES" }],
  total: int, page: int, page_size: int }
GET /autopilot/history/{batch_id}/files -> { items: [{ id, source_file_id,
    source_file_name, content_hash, ingested_at, status, error_detail }] }
GET /autopilot/history/legacy/files      -> same shape, for the batch_id: null bucket
```

`_derive_run_status()` collapses a run's file statuses: all succeeded → `SUCCESS`; any failure alongside any success **or skip** → `PARTIAL`; failures and nothing else → `FAILED`; the marker row alone → `NO_NEW_FILES`; every file a duplicate → `SUCCESS` with `imported: 0` (dedup working is the system doing its job, not an error). `files_seen` excludes the marker row, so an empty run reports `files_seen: 0` rather than claiming to have processed a file it never saw.

Run totals are **derived** from the file rows rather than stored in a summary row — a summary row would be a second copy of facts that can drift out of agreement with the rows it summarizes.

Legacy rows (`batch_id IS NULL`) collapse into **one** synthetic item with `batch_id: null`/`trigger: null`, always ordered last and occupying exactly one slot in the paged ordering — one "before run tracking" bucket rather than thousands of one-file pseudo-runs. Its files come from `GET /autopilot/history/legacy/files`, declared **before** the `/{batch_id}/files` route because FastAPI matches in declaration order and `legacy` is not a UUID. `get_run_files()` filters on `tenant_id` as well as `batch_id` and returns **404** for both an unknown id and another tenant's id — deliberately indistinguishable, so the endpoint cannot be used to probe which run ids exist.


**Sync history can be hidden by the user and is pruned over time (Gap 429, 2026-09-04).** Before this, `tenant_autopilot_logs` was append-only and permanently visible: a tenant could not remove a run from the Sync History screen, and the table grew forever — an unattended scheduler writes at least one row (usually a `NO_NEW_FILES` marker or a `SKIPPED_DUPLICATE`) on every single pass.

The constraint that shapes the whole design: **this table is not only the history read model.** `run_sync()` uses it as dedup layer 1 (`source_file_id` + `status == 'SUCCESS'`), dedup layer 2 (`content_hash` + `status == 'SUCCESS'`) and the incremental-poll watermark (latest SUCCESS `ingested_at`). Removing a SUCCESS row would make Autopilot re-download, re-store, re-charge quota for and re-extract an invoice it had already ingested. So:

1. **User-facing "delete" is a soft delete.** `TenantAutopilotLog.hidden_at: datetime | None` (NULL = visible; migration `b2c3d4e5f6a8`). `DELETE /autopilot/history/{batch_id}` stamps `hidden_at = now()` on that run's rows; `DELETE /autopilot/history` does it for every visible row of the tenant. Both return `{ "hidden": <rows changed> }`, counting only rows that were visible before the call — so hiding an already-hidden run reports 0, and clearing an empty history is `{"hidden": 0}` rather than an error.
2. **Every read path filters `hidden_at IS NULL`; no dedup or watermark query does.** `get_autopilot_history()` folds the predicate into its shared `tenant_filter`, so the two counts, the grouped page and the legacy aggregate all inherit it and a fully hidden run drops out of `total` as well as out of `items` (otherwise the pager would reserve slots for rows it never renders). `get_run_files()` and `get_legacy_run_files()` filter it too — hiding a run must close its drill-down URL, not just remove the list row. The three queries in `run_sync()` that must **not** filter it carry an explicit comment saying why.
3. **Retention hard-deletes noise only.** `services/autopilot_sync.py::prune_autopilot_history()` walks every `TenantAutopilotConfig` and deletes rows older than that tenant's `history_retention_days` whose status is in `SKIPPED_DUPLICATE`, `FAILED`, `NO_NEW_FILES` (`_PRUNABLE_STATUSES`). **SUCCESS rows are never hard-deleted at any age** — they can only be hidden. The prunable three carry no dedup meaning (a skip is the record of a decision made by consulting a SUCCESS row; a failure ingested nothing; a marker says a run happened) and they are exactly the rows that accumulate.
4. **`history_retention_days` is per tenant**, default 90, bounded **7–365** by `AutopilotConfigPayload` (a 422 at the edge, not just a DB constraint). It round-trips through `GET`/`PUT /autopilot/config`; a client that omits the field gets the default, so the existing FE payload keeps working.
5. **Scheduling.** `run_sync_for_all_due_tenants()` calls the prune once per scheduler pass, *before* the per-tenant syncs, so a pass that dies partway through has still trimmed the table. A module-level `_last_prune_at` limits it to once per `_PRUNE_INTERVAL` (24h) — an optimisation, not a correctness guarantee: the job container restarts regularly and an extra prune within the same day simply deletes nothing.

```
DELETE /autopilot/history/{batch_id} -> { hidden: int }     # batch_id may be "legacy"
DELETE /autopilot/history            -> { hidden: int }
```

`batch_id` is typed `str` rather than `UUID` on the hide route for one reason: the history list contains one item whose id is not a UUID — the synthetic `"legacy"` bucket of pre-Gap-427 rows. A malformed id therefore returns **404**, not 422, matching `get_run_files()`'s rule that an unknown id, another tenant's id and an already-hidden run are all indistinguishable from each other.
