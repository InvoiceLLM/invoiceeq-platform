# Feature 11: PayU Billing API

Implement PayU's classic hash-based checkout flow and the `surl`/`furl` confirmation handlers to auto-manage tenant plan upgrades and payment lockouts.

Provider decided 2026-07-31: **PayU**, not Stripe or Razorpay. Stripe stopped onboarding new India-domiciled merchants in 2022. Razorpay's signup also gates basic account creation behind PAN (even for test mode). PayU was chosen specifically because it publishes public sandbox test credentials usable with zero account setup, and — once a real account was created (Individual/Proprietorship business type, personal PAN, no GST/company registration needed) — its Merchant Key + Salt pair was **verified working end-to-end against PayU's live test environment on 2026-07-31**: `verify_payment` API call succeeded, the hash-signed checkout form was accepted by PayU's hosted payment page, a test card passed through 3DS2 simulation and OTP entry. The only failure was at final settlement, consistent with the account not yet having KYC/bank details on file — not an integration defect.

### Functionality
* `create_checkout_session()`: Accepts a target plan (`pro` or `pro_combined`), generates a `txnid`, and computes the PayU request hash:
  `sha512(key|txnid|amount|productinfo|firstname|email|udf1|udf2|udf3|udf4|udf5|udf6|udf7|udf8|udf9|udf10|salt)` — with `udf1`-`udf10` empty (unused for now; `udf1` is reserved for `tenant_id` if a future field is needed for reconciliation instead of relying solely on `txnid`).
  Returns the full field set (`key`, `txnid`, `amount`, `productinfo`, `firstname`, `email`, `hash`, `surl`, `furl`, `action_url`) for the frontend to render as a hidden auto-submitting form POSTing to PayU's hosted page (`test.payu.in/_payment` or `secure.payu.in/_payment`, selected by `PAYU_MODE`).
* `payu_success()` / `payu_failure()`: PayU POSTs the transaction result directly to these URLs (configured as `surl`/`furl` on each checkout request — there is no dashboard-configured webhook in PayU's classic flow). Because a bare POST to a public URL can be spoofed by anyone, **the response is never trusted on its own**:
  1. Verify the response hash PayU sends back: `sha512(salt|status|udf10|udf9|udf8|udf7|udf6|udf5|udf4|udf3|udf2|udf1|email|firstname|productinfo|amount|txnid|key)` (reverse field order of the request hash, with `status` inserted after `salt`).
  2. Cross-check server-to-server via PayU's `verify_payment` API (`command=verify_payment`, `var1=txnid`, its own `sha512(key|verify_payment|txnid|salt)` hash) — this is the same API call already manually verified working against the real PayU sandbox.
  3. Only if both checks agree does the handler update `Tenant.billing_plan` to `'pro'`/`'pro_combined'` and set `Tenant.payu_subscription_id = txnid`.
* **Renewal model**: PayU's classic API is one-time-payment, not a native recurring/subscription object like Stripe or Razorpay. This feature implements **manual monthly re-payment** — the tenant re-runs `create_checkout_session()` each billing cycle (prompted by the app, e.g. an in-app banner near cycle end) rather than true auto-debit. PayU's separate Standing Instruction (SI) product could enable real auto-renewal later; deliberately out of scope until this MVP ships and SI is separately researched.
* Note: The auth middleware `dependencies.py::get_tenant_context()` already checks for `'unpaid'` and blocks access with a `402 Payment Required` exception — this feature only needs to *set* that state (via a lapsed-renewal check, not a webhook-driven cancellation event, since PayU has none), not build the enforcement itself. **That setting half was built 2026-08-04 — see "Billing lapse enforcement" below.**

#### Billing lapse enforcement (built 2026-08-04, closes Gap 71)

From Feature 11 shipping until this landed, the 402 gate was dead code: nothing anywhere ever assigned `billing_plan = 'unpaid'` outside test files, so a tenant could complete one checkout and keep paid-tier access indefinitely. PayU's classic API has no subscription object and no cancellation webhook, so lapse cannot be *received* as an event — it has to be *inferred from a date*.

* **`Tenant.paid_through` (migration `a4b5c6d7e8f9`)** is that date: the end of the currently-paid-for cycle. `_handle_payu_callback()` calls `extend_paid_through()` alongside the existing `billing_plan`/`payu_subscription_id` writes, so every verified payment pushes it forward one `BILLING_CYCLE_DAYS` (default 30). It extends from **whichever is later, now or the existing `paid_through`** — a tenant renewing five days early keeps those five days instead of silently forfeiting them; a tenant renewing forty days late gets a cycle starting now rather than one that already elapsed.
* **`services/billing_lifecycle.py` owns all the date arithmetic in one place**, deliberately, so the two enforcement paths cannot drift on what "lapsed" means. Two non-behaviours are load-bearing: `paid_through IS NULL` is *never* lapsed (that's every free tenant and every row predating the migration — lapsing them would have locked out real paying customers the moment it deployed), and only `PAID_PLANS = {"pro", "pro_combined"}` can lapse (`free` has its own `free_invoices_remaining` quota enforcement, refilled on its own cycle as of Gap 118 — see below; `active` is the mock/dev plan). `BILLING_GRACE_PERIOD_DAYS` (default 3) sits after `paid_through` so a payment landing a few hours late doesn't lock anyone out.
* **Lazy per-request enforcement** in `get_tenant_context_allow_unpaid()`: one datetime comparison against a `Tenant` row that request already loaded, then `enforce_lapse()` writes the demotion — but only on the single request that actually crosses the boundary, since afterwards the plan is `'unpaid'` and `is_lapsed()` short-circuits on the plan check. Chosen over a scheduler-only design because it needs no new infrastructure (this repo has no scheduler) and takes effect on the very next request. Demotion is **persisted** rather than computed on the fly so the tenant row itself shows the state — support and reporting queries reading `billing_plan` agree with the API instead of having to re-derive lapse.
* **`scripts/sweep_lapsed_billing.py`** (`sweep_lapsed_tenants()`) covers what the lazy check structurally cannot: a tenant who stops paying *and* stops making requests would otherwise sit on `'pro'` in the database forever. Idempotent (a demoted tenant is no longer in `PAID_PLANS`, so it isn't a candidate next pass) and has a `--dry-run` mode. Deliberately a standalone entrypoint, not a task registered with a scheduler, since none exists here yet — an Azure Container Apps scheduled job or cron can drive it with no code change.
* **`get_tenant_context()` was split** into `get_tenant_context_allow_unpaid()` (resolve + lapse check, no 402) and `get_tenant_context()` (that, plus the 402 gate). This split is not cosmetic — it fixes a lockout that only became reachable once lapse actually fired. `create_checkout_session()` depended on `get_tenant_context()`, so an `'unpaid'` tenant would have been 402'd out of **the very endpoint that takes their payment**, making lapse a one-way door. Checkout and `GET /auth/me` now use the allow-unpaid variant; `/auth/me` because it is the FE's identity source (`hooks/useAuth.ts`) and 402ing it would leave the app unable to read its own `billing_plan`, so it could neither explain the lockout nor route the user to checkout. Every other endpoint is unchanged.

#### Free-tier quota refill (built 2026-08-04, closes Gap 118)

The free tier was always described as **50 invoices a month**, but was implemented as a decrement-only counter: `upload_invoices()` and `start_directory_watcher()` both do `tenant.free_invoices_remaining -= len(files)` and nothing anywhere ever put it back. `Tenant.free_invoices_remaining` was seeded once at row creation (`default_factory` → `DEFAULT_FREE_INVOICES_LIMIT`), so in practice the free tier was 50 invoices for the **lifetime of the account**, after which the tenant was permanently 402'd with "Limit reached" and the only exit was paying.

This is the same shape of problem as Gap 71's lapse — a state change that can only be inferred from a date, with nothing evaluating that date — so it was deliberately built as the mirror image of it, in the same module, rather than as a second mechanism:

* **`Tenant.free_quota_reset_at` (migration `c6d7e8f9a0b1`)** is the refill date. Nullable, no `server_default`, **no backfill** — exactly the shape `paid_through` chose, for the same reason. NULL means "the cycle clock has not started for this row", which is true of every pre-migration tenant. Backfilling to `now()` would have made the deploy itself a mass grant of 50 invoices to every free tenant; backfilling to a past date would be inventing an anniversary that was never observed.
* **`refresh_free_quota()` has three outcomes, and only one is a refill.** Not on the free plan → nothing at all. On the free plan with no clock yet → seed `free_quota_reset_at` one cycle out, commit, and **leave the counter alone** (returns `False`); the tenant keeps whatever balance they have and gets their first refill one full cycle later. Past the deadline → counter back to `DEFAULT_FREE_INVOICES_LIMIT`, deadline advanced, commit (returns `True`).
* **Only `FREE_PLAN = "free"` refills.** `'unpaid'` is excluded and that exclusion is load-bearing: it is what Gap 71 demotes a lapsed payer to, so refilling it would hand a non-paying tenant a free tier as a reward and quietly undo the demotion. This is the same reasoning that already made `LAPSED_PLAN` `'unpaid'` rather than `'free'`.
* **`advance_free_quota_reset_at()` advances by whole cycles from the existing date**, not to `now + cycle`. A tenant idle for three months lands back on their original monthly anniversary in one pass instead of having their refill date silently drift to whenever they happened to return — the same "extend from the existing date, not from now" intent as `extend_paid_through()`, applied to a date that may be several cycles stale.
* **`FREE_QUOTA_CYCLE_DAYS` is its own setting**, not a reuse of `BILLING_CYCLE_DAYS`, despite both defaulting to 30. `BILLING_CYCLE_DAYS` means "how much time one PayU payment buys"; if a future annual plan pushed it to 365, reusing it would silently turn the free tier into 50 invoices per *year*. Same number today, different meaning, so they are separate knobs.
* **Wired lazily in `get_tenant_context_allow_unpaid()`, immediately after `enforce_lapse()`** — same request path, same rationale (no scheduler exists; it costs one datetime comparison against a `Tenant` row the request has already loaded; the write happens only on the request that actually crosses the boundary). Placed at the dependency rather than at the two upload call sites so the tenant's allowance is already correct whichever door they come in through, including a page that merely reads the counter. **Ordering after the lapse check is deliberate**: a tenant demoted to `'unpaid'` on that very request must not then be handed a fresh free allowance by the refill running microseconds later — `refresh_free_quota()` only acts on `'free'`, and there is a test pinning that exact interleaving.
* **Not covered here**: a free tenant who exhausts their quota and then stops making requests entirely keeps a stale `free_invoices_remaining` in the database until they next show up (at which point they are refilled correctly before anything reads it). That is a reporting-accuracy gap, not a user-facing one, and is Gap 121 — the free-tier equivalent of `sweep_lapsed_billing.py`, deliberately out of scope for this change.

#### Reading the allowance back out — `GET /billing/usage` (built 2026-08-12, closes FE Gap 143's backend half)

Everything above *writes* the quota; nothing ever exposed it for reading, so the Subscriptions & Billing screen derived its own usage figure and got it wrong twice over (`GET /invoices?limit=1`, whose count is an `X-Total-Count` **header** and not the `data.total` body field the page looked for, compared against a client-side `planLimit` whose free-tier value said 25 where `DEFAULT_FREE_INVOICES_LIMIT` says 50). `get_billing_usage()` returns the counters themselves so the number on screen and the number that produces a `402` are the same number by construction.

* **Derived from `free_invoices_remaining`, never from a row count.** An invoice count could not have reconciled with the gate even if read correctly: the gate reads a monthly decrement-only counter, while `GET /invoices` counts `flow_direction == "INBOUND"` rows for the lifetime of the account, which never drops at a cycle reset.
* **`metered` is the honest answer to "does this plan have an allowance at all".** Only `free` does — `routers/invoices.py` consults `free_invoices_remaining` exclusively under `billing_plan == "free"` — so every other plan returns `metered=False` with `used`/`limit`/`remaining`/`resets_at` all null rather than a fabricated ceiling. Deliberately says nothing about the Pro tier's advertised 1,000/month cap: that cap does not exist in the software, and whether it should was BE Gap 188's decision, not this endpoint's to pre-empt. **Resolved 2026-08-12 (Gap 188, closed)**: the decision was that 1,000/month is marketing copy, not a limit — the Pro card in `invoice-fe/app/settings/subscriptions/page.tsx` now reads "Unlimited invoices" and **no Pro-tier counter or gate was added**, so `metered=False` for `pro`/`pro_combined` is the permanent, intended contract rather than a placeholder awaiting enforcement.
* **No Admin gate**, unlike `create_checkout_session()`. This is a read of the caller's own workspace allowance, and a non-Admin who can ingest invoices is exactly who runs into the `402` this number predicts. Changing the plan stays Admin-only.
* **`get_tenant_context_allow_unpaid`, for the same reason checkout uses it** (Gap 71): a lapsed tenant opens this page precisely to fix their billing, so the page's own data call must not `402` out from under them.
* **Read-only, and correct without doing any work of its own.** `refresh_free_quota()` already runs in the dependency on every request (Gap 118), so a tenant whose cycle elapsed while idle is refilled *before* the handler reads the row — the endpoint never has to re-derive a reset.
* **Clamped to `[0, limit]`.** BE Gap 189 (open) can drive the counter negative under concurrent uploads, and a row seeded before `DEFAULT_FREE_INVOICES_LIMIT` last changed can hold more than the current limit; neither may render as a negative or over-full bar. The clamp is presentation-side only — it does not paper over Gap 189, which remains a real spend-side defect.

#### Granting a paid plan for QA on a deployed environment (built 2026-08-04, closes Gap 117)

`dependencies.MOCK_BILLING_PLAN = "active"` only applies when `ALLOW_MOCK_AUTH` is on — i.e. local dev with no real Clerk. On a **deployed** dev environment with real Clerk auth, a tenant's plan comes from exactly one place: the verified PayU callback. Testing anything gated on `'pro'`/`'pro_combined'` therefore meant running a full PayU sandbox checkout by hand, per tenant, every time a cycle lapsed. The Gap 104 `/admin` console edits a user's *role*, never `billing_plan`, so it was no help either.

**`scripts/grant_test_plan.py`** fills that hole, following the same standalone-entrypoint, direct-DB-mutation pattern as `sweep_lapsed_billing.py` (same `sys.path` bootstrap, same `argparse` + `--dry-run` shape, same `Session(engine)` usage, logging rather than printing):

* `--tenant` accepts an id **or** a domain; a value that parses as a UUID is only ever looked up as an id, so a domain can never be silently matched against something that merely looks like one.
* `--plan` is constrained to `sorted(PAID_PLANS)` — imported from `billing_lifecycle`, so it cannot drift from the set of plans that `is_lapsed()` recognises.
* `--cycles` (default 12, ≈1 year) calls **`extend_paid_through()` once per cycle** rather than inventing a separate "far future" date here, so a granted plan is byte-identical in shape to a paid one and `extend_paid_through()` stays the single definition of "one cycle".
* `payu_subscription_id` is deliberately **not** set. There is no transaction; forging a txnid would make a hand-granted plan indistinguishable from a real payment in support queries.
* **Two independent guards, both must pass** (`assert_non_production()`, split out from `main()` specifically so the guard itself is testable — an unexercised safety check is not a safety check):
  1. `settings.ENVIRONMENT` must be in `NON_PRODUCTION_ENVIRONMENTS` (`dev`, `development`, `local`, `test`, `testing`, `qa`, `staging`). `ENVIRONMENT` is new in `config.py` and **defaults to `"production"`** — the same fail-closed choice as `ALLOW_MOCK_AUTH`, so an environment that never declared itself refuses, and a typo (`prod-eu`) refuses rather than being assumed safe.
  2. `settings.PAYU_MODE` must not be `"live"`. This is defence in depth against the realistic accident that guard 1 cannot catch on its own: exporting `ENVIRONMENT=dev` in a shell that happens to point at the production database. A real production deployment must have `PAYU_MODE=live` for payments to work at all, so it is a much harder signal to fake by accident.
* Neither guard is a security boundary — anyone who can run this already holds the database credentials. They exist to stop an accident, and they are the reason this stays a script and never becomes an API endpoint. `ENVIRONMENT` is read **only** by this script; no request-handling code branches on it.
* **Deployment note**: nothing in `infra/` sets `ENVIRONMENT` on any Container App yet, so on the deployed dev environment the operator supplies it at invocation (`ENVIRONMENT=dev uv run python scripts/grant_test_plan.py ...`). Adding it to the dev container app's env block is a one-line infra follow-up, owned by infra-devops, not done here.

#### Callback reachability and the return flow (built 2026-08-02)

* **Where the callback physically lands.** `invoice-be`'s Container App ingress is `external: false`, so PayU — a third party on the public internet — can never POST `surl`/`furl` at it. `invoice-website` is the only public origin, so it carries a verbatim pass-through at the *identical* path shape the backend serves: `POST /api/v1/billing/payu/success` and `.../failure` (`relay.ts::relayPayuCallback()`). `create_checkout_session()` therefore keeps building `surl`/`furl` as `{BACKEND_PUBLIC_URL}/api/v1/billing/payu/{success,failure}` unchanged — only the *value* of `BACKEND_PUBLIC_URL` changes, from invoice-be's origin to invoice-website's. Three properties of that relay are load-bearing:
  1. **Unauthenticated.** Unlike the sibling `/api/billing/create-checkout-session` proxy, there is no Clerk `auth()` gate — PayU carries no session, and a gate would break the callback outright. This does not weaken anything: `_handle_payu_callback()` verifies the response hash *and* runs the independent `verify_payment` cross-check before trusting a single field, so a spoofed POST simply lands on `/billing/failed`.
  2. **Verbatim forward.** Method, `Content-Type`, and the raw `application/x-www-form-urlencoded` body are passed through untouched — the response hash covers those exact bytes, so any normalisation would break verification.
  3. **The 303 is relayed, not followed** (`redirect: "manual"` + re-emitting `Location`). Letting `fetch` follow it server-side would return the landing page's HTML with a `200` instead of a browser redirect — the same mistake already made and fixed once in this repo on the connectors OAuth callback (`fe_features_tracker.md` Gap 98's follow-up).
  If the backend is unreachable from the relay, it does **not** 500 at a user who may have just paid: it redirects to `/billing/failed?reason=unverifiable&txnid=…`, reading `txnid` out of PayU's own POST body for display only (never for a trust decision).
* **Where the user lands.** `/billing/success` and `/billing/failed` are **invoice-website** routes, not invoice-fe ones. Post-Multi-Zone-proxy (`website_features_tracker.md` Gap 12) invoice-fe is `ingress.external: false`, so a browser returning from PayU cannot reach an invoice-fe URL at all; invoice-website is the only public origin, already owns the other half of this flow, and its `next.config.js` `fePages` proxy list deliberately excludes `billing`, so there is no route collision. Both pages are **public — no Clerk gate**: a user returning from PayU's hosted page may have no live session in that tab, and bouncing them to login would make a successful payment look broken.
* **`/billing/success` makes no API call.** `_handle_payu_callback()` has already committed `tenant.billing_plan` and `tenant.payu_subscription_id` before issuing the redirect, so the page is purely informational (plan name, price, transaction reference, links onward into the app). Deliberate: a fetch on that page could fail and make a successful payment *look* failed.
* **`/billing/failed` maps the real backend outcomes to three severities**, and must not flatten them into one "payment failed" message:
  | Query params emitted by `_handle_payu_callback()` | Severity | What the page says |
  |---|---|---|
  | `?txnid=…` (no `reason`) | `declined` | PayU's own records confirm the transaction didn't complete. Safe to retry — primary CTA is "Try the checkout again". |
  | `?reason=malformed` | `unconfirmed` | Callback had no `txnid` at all; we can't tell what happened. Check your bank before paying again. |
  | `?reason=hash_mismatch&txnid=…` | `unconfirmed` | Signature didn't verify, so we refused to act — but that doesn't mean the money stayed put. **No retry CTA**; contact support with the reference. |
  | `?reason=unverifiable&txnid=…` | `unconfirmed` | `verify_payment` couldn't be reached. Same treatment. |
  | `?reason=unknown_plan&txnid=…` | `charged_not_applied` | Payment *verified as successful*, `productinfo` didn't map to a plan. The user **has** been charged. **No retry CTA.** |
  | `?reason=unknown_tenant&txnid=…` | `charged_not_applied` | Same, but `udf1` didn't resolve to a tenant. |
  | no params | `declined` | Nothing to go on; offer the pricing page. |
* **`PUBLIC_APP_URL` vs `FRONTEND_URL`.** `FRONTEND_URL` was serving two unrelated purposes: billing's user-facing return redirects, and `connectors.py::oauth_callback()`'s redirect to `/settings/connectors` (an **invoice-fe** route). Post-proxy both resolve through the website origin, but only when `ENABLE_FE_PROXY=true`, which is not the case in local dev where invoice-fe serves itself on :3001. Billing was therefore split onto its own `PUBLIC_APP_URL` — "the one origin a browser can actually reach" — leaving `FRONTEND_URL`'s semantics and every connectors code path untouched. In Azure both point at invoice-website's FQDN; in local dev they can differ.
