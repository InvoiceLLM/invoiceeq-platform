  1. **How the 3-tabs symptom on this specific account led here**: `apps/invoice-website/app/signup/page.tsx` hardcoded `unsafeMetadata: { ..., role: "admin,user" }` (two places) on signup — a comma-joined string, not a real role token. `RoleMapper.normalize_role()` couldn't map it to `"Admin"` (no match in `ROLE_ALIAS_MAP`, falls through to `.title()`), so this user's permissions all resolved `False`. Fixed the two literal strings to `"admin"` (commit `0753762`). Confirmed via the Clerk export (`clerk_export_20260807_191255.json`) that this exact bug was present on **all 7** users on the old Clerk account too — it just never mattered there, because the old account's `invoice-app` JWT Template only requested `email`/`org_id`/`org_role` claims, never `role`. The new account's template (pre-existing, not something this session configured) additionally requests `"role": "{{user.unsafe_metadata.role}}"` — newly surfacing a bug that had been dormant and harmless for as long as the app existed.
  2. **The real finding, once that was traced through**: `dependencies.py::get_tenant_context_allow_unpaid()` resolved role as `payload.get("role") or payload.get("org_role", "Viewer")` — the `role` claim (sourced from `unsafe_metadata`, which Clerk's client SDK lets *any signed-in user freely rewrite on themselves*, e.g. `Clerk.user.update({ unsafeMetadata: { role: "admin" } })` from a browser console, no backend call involved) was checked **before** `org_role` (sourced from real Clerk Organization membership, changeable only via Clerk's own permission-checked Organizations API or the Dashboard). This meant any authenticated user — including the majority added via Settings' "add user" flow, who the code deliberately never gives Admin (see `admin.py`'s `create_user`/`set_permissions`: hardcodes `role="Viewer"`, comment: *"Admin is never granted by this endpoint, only by the Clerk-side role the JWT carries"*) — could self-grant Admin purely client-side.
  3. **First fix, insufficient alone**: reordering to prefer `org_role` only closes the hole for users who are real Clerk org members. Settings-added users (confirmed via `apps/invoice-fe/app/api/admin/create-user/route.js`: calls Clerk's bare `POST /v1/users`, never adds them to the Organization) have **no `org_role` at all, ever** — for them `role` is the only signal, so a plain reorder still leaves them able to self-escalate. Fixed by clamping: when `org_role` is absent, a `role` claim that resolves to `"Admin"` is explicitly downgraded to `"Viewer"` rather than trusted.
  4. **Second, deeper hole, found when the user pushed back on whether the first fix was actually complete**: `org_role` is only meaningful for whichever Clerk Organization is currently *active* on the session — and Clerk lets any signed-in user self-serve `Clerk.createOrganization({name: "..."})`, which makes its creator that new org's `org:admin` automatically, no spoofing needed, entirely real Clerk-issued data. The existing-user branch applied `role` (freshly computed from whatever org happened to be active in that request's token) straight onto `user.role` with no check that the token's `org_id` matched the org the user's *actual* tenant was tied to — so any existing Viewer could self-escalate on their real tenant just by creating-and-activating a throwaway org of their own. Fixed by gating the role update on `clerk_org_id == tenant.clerk_org_id` (or `clerk_org_id is None`, the already-clamped non-org-member case) — a role claim for an unrelated org no longer touches this user's stored role at all.
  - **Net result**: `role` (`unsafe_metadata`, client-writable) can now only ever produce non-Admin labels, and only ever updates a user's stored role when it comes from the org their tenant is actually tied to. The only path to `"Admin"` anywhere in this function is a real `org_role == "org:admin"` claim for that user's own tenant's org — which only Clerk's own permission-checked Organizations API (or the Dashboard) can grant.
  - **Live remediation for accounts already affected**: patched `unsafe_metadata.role` back to `"admin"` for the 4 real Clerk users already touched during this migration (`Clerk_payu@asd.com`, `sanjib@abcd.com`, `larzopil@fosil.pro`, `mbirla@infinevocloud.com`) and corrected their already-synced Postgres `role` values to match their real `org:admin` membership.
  - **Known residual edge case, not fixed here**: the tenant `clerk_org_id` backfill (`elif clerk_org_id and not tenant.clerk_org_id`) still fires even when `clerk_org_id` is for an unrelated org, if that tenant's `clerk_org_id` was never set to begin with. Narrow: only matters for a tenant with no `clerk_org_id` on record, and doesn't grant anything in the request that triggers it — worth tightening if it ever proves reachable in practice.
  - **Follow-up, same change**: `apps/invoice-fe/app/api/admin/create-user/route.js` used to never add the new user to the caller's Clerk Organization at all, so Settings-added users had no `org_role` at all — they were exactly the population the clamp in point 3 above exists to protect, permanently relying on it rather than ever getting the real `org_role` signal. Fixed by adding the new user to the caller's own org (`orgId` from the caller's own `auth()` session) as `"org:member"` immediately after creation, so `org_role` is now the uniform source of truth for every user, not just org creators. Also cleaned up the now-inert `unsafe_metadata: { role: 'user' }` → `'member'` (still harmless either way post-fix, `'user'` just wasn't a recognized `ROLE_ALIAS_MAP` key).
  - **FE half of the same fix — `apps/invoice-website/app/login/page.tsx`**: with `role` no longer trusted for authorization, the login page's Admin/User role picker and its Access Denied gate (which checked the selected role against the same `unsafeMetadata.role` string, comma-split) had no correctness purpose left — `Sidebar.tsx`/`useAuth()` already resolve real screens from `GET /auth/me` regardless of what was picked here. Removed entirely, along with the 2026-08-05 two-tab "Sign In / Create Organisation" mode switcher built around it (Gap 164) — with no role to pick, "Sign In" was the only tab left, so the tab row itself no longer earned its place. "+ Create Organisation" used to switch to an intermediate static pane with its own second button linking to `/signup`; now it's a direct link to `/signup`, no extra click. Dead styles/helpers removed: `S.roleRow`/`roleIcon`/`accessDenied`/`createPane`/`createIcon`/`createTitle`/`createCopy`/`createBtn`/`tabRow`, `roleBtnStyle()`/`tabBtnStyle()`. `tsc --noEmit` clean on the file both times.
  - **Docs updated for this entire gap**: `apps/invoice-website/website_features/feature_4_auth_gateway.md` (Functionality items 1, 2, 7), `apps/invoice-website/website_features/website_features_tracker.md` (Gap 164, superseded-by note added), `docs/test_cases/website/feature_4_auth_gateway_tests.md` (TC-WEB4-01/04/07/08/14/15). `apps/invoice-fe/docs/fe_features_tracker.md` and `feature_1_layout_theme.md` already documented `Header.tsx` avoiding `unsafeMetadata.role` for display (a separate, earlier, already-correct decision) — left as-is, still accurate.
