- `[x]` **Gap 182: RAG chat paid for two sequential LLM round-trips on every single message** — found + fixed 2026-08-10. `classify_query()` in `agents/query_agent.py` ran a full structured-output LLM call to route every message into SQL/RAG/CHAT, then a *second* LLM call to actually answer it — doubling latency on every chat turn even though a large share of real questions ("what's my total spend", "hello") are unambiguously classifiable by keyword alone. A keyword-based fallback classifier already existed but was only ever reached inside the `except` block if the LLM call itself raised, so it almost never actually ran. **Fix**: inverted the order — the keyword pass (`_SQL_KEYWORDS`/`_CHAT_KEYWORDS`, module-level constants) now runs first, free and instant, and only falls through to the LLM for genuinely ambiguous phrasing. - `[x]` **Gap 172: On a genuinely new Azure environment (`rg-invoice-llm-dev`), every authenticated FE→backend call 401'd with "Missing or malformed Authorization header" even after a real, valid Clerk token was confirmed being minted — root cause: internal `http://` calls against Container Apps ingress get 301-redirected to `https://`, and Node's `fetch()` strips the `Authorization` header on that scheme-change redirect** — found and fixed 2026-08-07, after an extended live investigation (real logs, live diagnostic builds, direct network tests — not guesswork) that ruled out several real-looking but incorrect theories along the way.
  1. **Symptom**: logging in as Admin on the new environment showed only 3 sidebar tabs (Dashboard/Chat/Help) — `Sidebar.tsx` gates the rest on role/permissions from `useAuth()`, which falls back to fully anonymous the moment `GET /api/auth/me` returns non-2xx.   4. **The actual final root cause**: fixing item 3 made FE reliably mint a real, valid ~800-character token (confirmed via live logs: `auth() resolved, userId: ...` / `getToken result, length: 821`) — but the backend **still** 401'd on every call. Traced with a raw Node `http.request()` test executed live from inside the FE container (`az containerapp exec`) against the backend's internal FQDN over plain HTTP: **`301` redirect to `https://` on the identical host**, because the backend's ingress has `allowInsecure: false` — which enforces HTTPS even for internal, same-VNet traffic, not just external.     2. `infra/modules/compute/invoice-website.bicep:83` — website's `BACKEND_API_URL`

Adopted as a standing rule for all future internal calls, not just these three.

- `[x]` **Gap 173: privilege escalation — any signed-in user could grant themselves Admin (or overwrite their role on their real tenant) via Clerk's own client SDK, no backend involved** — found and fixed 2026-08-07, while investigating why a brand-new signup ("New_org_clerk", `Clerk_payu@asd.com`) showed only 3 tabs despite being that org's own creator.

  2. **The real finding, once that was traced through**: `dependencies.py::get_tenant_context_allow_unpaid()` resolved role as `payload.get("role") or payload.get("org_role", "Viewer")` — the `role` claim (sourced from `unsafe_metadata`, which Clerk's client SDK lets *any signed-in user freely rewrite on themselves*, e.g. `Clerk.user.update({ unsafeMetadata: { role: "admin" } })` from a browser console, no backend call involved) was checked **before** `org_role` (sourced from real Clerk Organization membership, changeable only via Clerk's own permission-checked Organizations API or the Dashboard).   4. **Second, deeper hole, found when the user pushed back on whether the first fix was actually complete**: `org_role` is only meaningful for whichever Clerk Organization is currently *active* on the session — and Clerk lets any signed-in user self-serve `Clerk.createOrganization({name: "..."})`, which makes its creator that new org's `org:admin` automatically, no spoofing needed, entirely real Clerk-issued data.   - **Net result**: `role` (`unsafe_metadata`, client-writable) can now only ever produce non-Admin labels, and only ever updates a user's stored role when it comes from the org their tenant is actually tied to. The only path to `"Admin"` anywhere in this function is a real `org_role == "org:admin"` claim for that user's own tenant's org — which only Clerk's own permission-checked Organizations API (or the Dashboard) can grant.

- `[x]` **Gap 210: SQL case-normalization only rewrites `=` comparisons, not `IN (...)` or `LIKE '...'`** — **fixed 2026-08-12.** `agents/query_agent.py::_normalize_string_equality()` (`:143-191`) now runs three passes per column instead of one; the original `=` pass is byte-for-byte unchanged and still runs first. **`IN`**: `\b{column}\s+(NOT\s+)?IN\s*\(\s*({_IN_STRING_LIST})\s*\)` → `TRIM(LOWER(column)) IN (TRIM(LOWER('a')), TRIM(LOWER('b')))` — each value gets the identical `TRIM(LOWER(...))` treatment the single `=` value already got, i.e. the same mechanism replicated per element, not a different one. **`LIKE`**: `\b{column}\s+(NOT\s+)?LIKE\s*'([^']*)'` → `TRIM(LOWER(column)) LIKE LOWER('%pattern%')` — `LOWER` only, **no `TRIM` on the pattern side**, decided deliberately after checking whether the `=` rewrite generalizes: it doesn't, because a pattern is not a value and `TRIM` would silently change what it matches (`' Harbor%'` ≠ `'Harbor%'`), whereas `LOWER` leaves `%`/`_` wildcards intact.
