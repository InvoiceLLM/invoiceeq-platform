Expose aggregated database statistics and multi-dimensional filtering for backend dashboard operations.

### Functionality
`get_dashboard_metrics()` applies the optional `start_date`/`end_date`/`vendor_name`/`po_number`/`status` filters on top of the tenant scope and computes the money/ranking/series figures as real SQL `SUM`/`COUNT`/`GROUP BY` aggregates. (This paragraph previously described a Python pass over every matching `Invoice` row pulled into memory; that stopped being true at FE Gap 29, which moved the work into SQL — only `average_processing_time`/`extraction_accuracy` still need a per-row pass, and that pass fetches 4 narrow columns rather than full ORM rows.)

**Money is reported per currency, never blended (FE Gap 183, 2026-08-11).** `Invoice.currency` is nullable and was historically never set, so every aggregate groups on `UPPER(COALESCE(NULLIF(TRIM(currency), ''), 'USD'))` — normalization at *query* time only, with no migration, no backfill, and nothing written back to the row. `NULLIF`/`TRIM` folds an empty-string extraction into the NULL bucket; `UPPER` prevents `"usd"` and `"USD"` being reported as two currencies. The endpoint returns:

* `totals_by_currency` — one row per currency: `{currency, total_invoiced, paid_amount (status PAID), outstanding_amount (COMPLETED/AUDIT_REQUIRED/PROCESSING), at_risk_amount (AUDIT_REQUIRED only)}`, ordered by size.
* `top_vendors` — grouped by vendor **and** currency, each element `{vendor_name, currency, amount}`, sorted descending (FE takes the top 5 within each currency). A vendor billing in two currencies gets two rows; merging them would produce a figure belonging to neither.
* `spend_over_time` — grouped by date **and** currency, each point `{date, currency, amount}`, falling back to `created_at.date()` when `invoice_date` is unset, so the FE can draw one trendline per currency instead of a single line that jumps between scales.
* `active_alerts_count`, `invoices_by_status` counts, `average_processing_time` (a real `completed_at - created_at` measurement over invoices where `completed_at` is set, not a hardcoded mock), `extraction_accuracy`, and the AI-score metrics.

The flat `total_invoiced`/`paid_amount`/`outstanding_amount`/`at_risk_amount` scalars this endpoint used to return were **removed, not deprecated**. They were bare `func.sum(Invoice.grand_total)` calls across every currency the tenant had, so a $500 and a ₹40,000 invoice were reported as a single `40500` which the FE then labelled with one symbol. A blended figure has no correct label, so keeping it alongside the new shape would only invite something to render it again; every consumer was migrated in the same change and `test_blended_cross_currency_scalars_are_gone` guards the removal. No FX conversion is performed anywhere — amounts in different currencies are never added.

`get_trainer_impact()` (Gap 28) returns `rules_trained` (Global/vendor-specific `ExtractionTemplate` counts), `vendors_needing_rules` (≥2 flagged invoices, no template yet), and a real weekly `audit_rate_trend`.

`get_dashboard_insights()` (Gap 30) generates the AI-written strategic-recommendations text `docs/feature_2_dashboard.md` Gap 4 needs. It recomputes a small, LLM-scoped subset of the same aggregates (`totals_by_currency` with per-currency total-invoiced and at-risk figures, audit rate, top 5 vendors by spend, top 5 vendors needing a rule) into a JSON context blob, then makes one `get_llm().with_structured_output(DashboardInsightsSchema)` call explicitly instructed to ground every recommendation in a number from that blob and never invent one. **FE Gap 183**: those money figures were previously blended Python `sum()`s across all currencies, meaning the "grounding fact" handed to the model was arithmetic over incomparable units. They are now keyed by currency, ranked within a currency rather than across, and the prompt explicitly forbids adding, subtracting, averaging or otherwise combining amounts in different currencies, forbids stating a single overall cross-currency total, and requires naming the currency beside any amount quoted — no exchange rate exists anywhere in this system to make such a comparison valid. Each insight has a `title`, `detail`, and `severity` (`info`/`warning`/`critical`). Result is cached in Redis (`dashboard_insights:{tenant_id}`, 1-hour TTL, same inline-client pattern as Task 6.11's chat answer cache) so the LLM isn't called on every dashboard load. A failed/erroring LLM call degrades to `{"insights": []}` rather than a 500.
