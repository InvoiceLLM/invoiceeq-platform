# Feature 15: Outbound Webhooks

Let a tenant register an HTTP endpoint to receive real-time notifications when an invoice's status changes (supporting both Inbound and Outbound flows) instead of polling the API.

**Built 2026-07-29.** All 5 tasks complete; 14 new tests (`tests/test_webhooks.py`) plus live verification against the real API (SSRF rejection and valid creation both confirmed against the real local Postgres, not just mocks). Full suite 138/138 passing.

### Functionality (target design)
`WebhookSubscription` rows are tenant-scoped: `target_url`, a per-subscription `secret` (used for HMAC-SHA256 signing, never returned by the API after creation), and `subscribed_events` (subset of: `invoice.completed`, `invoice.audit_required`, `invoice.paid`, `invoice.rejected`, `outbound_invoice.sent`, `outbound_invoice.overdue`, `outbound_invoice.paid`). All hook points call `dispatch_webhook_event(tenant_id, event_type, payload)` right after their database commit.
duplicated logic at each call site. Delivery: POST the event payload with
an `X-Webhook-Signature` header (HMAC-SHA256 of the raw body using the
subscription's `secret`), 3 retries with exponential backoff on
non-2xx/timeout, and auto-disable (`enabled = False`) a subscription after
10 consecutive failures — surfaced in the settings UI so the tenant
notices instead of silently losing events forever.

**Delivery is asynchronous (Gap 194, 2026-08-12).** `dispatch_webhook_event()`
no longer performs the HTTP call. It resolves which subscriptions match and
enqueues one `deliver_webhook` task per subscription onto the same
`extraction-tasks-queue` every other background job in this repo uses;
`queue_worker/handlers.py::handle_deliver_webhook` → `deliver_webhook_now()`
owns the retries, the failure accounting and the delivery-log row. The
delivery job re-reads the subscription at delivery time, so a queued message
can't resurrect a subscription that was disabled, deleted or unsubscribed from
that event between enqueue and delivery.

**Security**: `target_url` is validated against SSRF at creation time —
reject URLs resolving to private/link-local/loopback IP ranges (a tenant
could otherwise point a webhook at internal infrastructure). Delivery
requests use a short timeout and don't follow redirects to an
unvalidated host.

- [x] **Task 15.4: Wire into the real hook points** — see File Coordinates above (locations corrected from this doc's original spec). Every dispatch call is wrapped in its own try/except — a webhook delivery failure never fails the invoice operation that triggered it.
- [x] **Task 15.5: Auto-disable after 10 consecutive failures + re-enable** — `consecutive_failures` resets to 0 on any successful delivery; hits `enabled=False` at the threshold. Re-enabling via `PUT .../{id}` with `enabled: true` also resets the counter to 0, giving the subscription a clean slate instead of immediately re-tripping on the next delivery with a stale count.
- [x] **Task 15.6 (Gap 126): scheduled `outbound_invoice.overdue`** — built 2026-08-12, the one event the original five tasks left without a trigger.
  * **Candidate rule is the dashboard's rule, in SQL.** `find_overdue_invoices()` selects `flow_direction == "OUTBOUND"` + `status == "SENT"` + `due_date IS NOT NULL` + `due_date < today` + `overdue_notified_at IS NULL` — the same predicate `routers/outbound_dashboard.py` computes `is_overdue` from, including the strict `<` (due *today* is not overdue). Duplicating the rule loosely would have meant firing webhooks for invoices the tenant's own dashboard doesn't call overdue.
  * **Fires once per invoice, ever.** An unpaid invoice is overdue again every subsequent day, so a marker column was unavoidable — without it a daily job re-delivers the same event forever. `sweep_overdue_invoices()` stamps and commits `overdue_notified_at` **before** dispatching, making this deliberately at-most-once: `dispatch_webhook_event()` swallows its own delivery failures (it has its own 3-attempt retry), so a "mark only on success" ordering couldn't tell a failed delivery from a successful one and would only add a crash window in which a delivered event gets re-delivered.
  * **Overdue is still not a status.** The sweep writes only `overdue_notified_at`; nothing writes `OVERDUE` to `Invoice.status`, so no existing status filter, dashboard metric or FE tab changes shape. The comments in `routers/outbound_invoices.py::_dispatch_outbound_webhook` and `routers/outbound_dashboard.py` that previously said "no scheduled job" were updated to point at the sweep.
  * **Payload** adds three fields the transition-driven events have no use for: `due_date`, `days_overdue`, `currency` (alongside the shared `invoice_id`/`status`/`customer_name`/`grand_total`).
  * **Infra.** `infra/modules/compute/scheduled-job.bicep` is the repo's first `Microsoft.App/jobs` resource — cron `triggerType: 'Schedule'`, `parallelism: 1` / `replicaCompletionCount: 1` (two parallel replicas would both read the same un-notified rows), `replicaRetryLimit: 0` (the entrypoint is idempotent and re-runs on the next schedule anyway). It is parameterised on `command`/`args`/`cronExpression`/`jobName`, not hard-wired to the overdue sweep, so a second scheduled job (e.g. Gap 183 Autopilot) is another `module` block rather than a copy of the file. Env/secret shape mirrors `queue-worker.bicep`; it carries the six settings `config.py` has no defaults for (`DATABASE_URL`, `REDIS_URL`, `CHROMA_HOST`, `CHROMA_PORT`, `CLERK_SECRET_KEY`, `TOKEN_ENCRYPTION_KEY`) plus storage/OpenAI for future jobs. Wired in `infra/08-apps.bicep` as `caj-overdue-sweep-<env>` on the `backendImage` (that's where `scripts/` ships).

- [x] **Task 15.7 (Gap 194): async delivery, scoped auto-disable, delivery log** — built 2026-08-12. Three separate defects, fixed together because they all live on the delivery path:
  * **Async dispatch.** `_deliver_with_retry()` runs 3 attempts at a 5s timeout with 1s/2s backoff — up to ~19s, *per subscription*, and it ran inline on whatever thread had just committed the invoice (`queue_worker/handlers.py::handle_process_invoice`, `routers/audit.py`, `routers/outbound_invoices.py`, `services/outbound_overdue.py`). `dispatch_webhook_event()` now only enqueues (`_enqueue_delivery()` → `{"task": "deliver_webhook", "kwargs": {tenant_id, subscription_id, event_type, payload}}` on `extraction-tasks-queue`), matching the existing enqueue pattern in `services/invoice_reconciliation.py::_enqueue` and `queue_worker/handlers.py::_enqueue_process_invoice`. No call-site signature changed. An enqueue failure is recorded as a failed `WebhookDeliveryLog` row (`"Not queued: ..."`) but deliberately does **not** count toward auto-disable — failing to reach our own queue says nothing about the subscriber's health.
  * **Failure tracking scoped per event type.** Auto-disable stays *per subscription*, and deliberately so: a `WebhookSubscription` row is one target URL and one signing secret, so "disabled" can only mean "stop calling this URL" — a per-event-type enable flag would be a different, larger feature. What was actually wrong was the *counting*: a single flat `consecutive_failures` meant a subscriber that 500s on `outbound_invoice.overdue` while happily accepting `invoice.completed` took the whole endpoint offline after 10 overdue sweeps. `record_delivery_result()` now counts into `event_failure_counts` (`{event_type: consecutive failures}`) and trips `enabled = False` only when the failing event type has hit `MAX_CONSECUTIVE_FAILURES` **and** no other event type on the subscription is currently healthy (none has a count of 0, i.e. none delivered successfully last time). A genuinely dead endpoint fails every event type it is sent, so it still auto-disables exactly as before. `consecutive_failures` is kept in sync as `max(event_failure_counts.values())`, so the public API shape and the settings-page health warning keep working. Rows predating the column are lazily backfilled (the old flat count is attributed to the first event type that fails after the upgrade) rather than being handed a free reset. Re-enabling via `PUT` clears the map as well as the total — clearing only the total would leave the subscription one failed delivery from re-disabling.
  * **Delivery log.** `WebhookDeliveryLog` records one row per *attempt series* (the 3-attempt retry counts as one row, with `attempts` recording how many HTTP calls it took), with the HTTP status or transport error that `_deliver_with_retry()` previously threw away into a `logger.warning`. Exposed at `GET /api/v1/webhooks/{id}/deliveries?limit=` (newest first, tenant-scoped through the same subscription lookup as every other route in the file, so a guessed subscription id from another tenant is a 404). `DELETE /webhooks/{id}` clears the subscription's log rows — the table has no FK to the subscription (it is written from the queue worker and outlives individual attempts), so they'd otherwise be unreachable orphans. `error` never contains the payload or the signing secret.
  * **Known limitation, not built:** `webhook_delivery_logs` has no retention/trim policy — rows accumulate until the subscription is deleted. The tracker's suggested "(b) alert the tenant when auto-disable trips" is also still not built; auto-disable remains visible only via the settings page (health warning + delivery log), not pushed.
