# Feature 7: Audit Resolution & Finalization — **SENTINEL Agent**

**SENTINEL** is the Invoice Risk Detection agent. Enable human auditor overrides, update database transaction states, and save template learning rules.

### File Coordinates
* Router: [apps/invoice-be/routers/audit.py](file:///c:/Users/S%20Banerjee/Desktop/Invoice_LLM/Prod_Invoice_LLM/apps/invoice-be/routers/audit.py) → `PUT /audit/resolve/{invoice_id}` → `resolve_audit_invoice()`

### Functionality
`resolve_audit_invoice()` fetches the tenant-scoped `Invoice` row by id (no status filter — this works on an invoice in any status, not just `AUDIT_REQUIRED`; see Gap 53 below), then: (1) filters `invoice.sa_alerts` down to whatever wasn't named in `payload.dismissed_alerts` (matching by string, `id`, `type`, or `message` — alerts can be stored as either plain strings or dicts, so both shapes are handled); (2) if `payload.status` is present, validates it's `PAID`/`REJECTED` and writes it — `status` is optional, so a call can dismiss alerts and/or save corrections without finalizing the invoice at all; (3) if `payload.corrections` is present, persists each corrected field onto the `Invoice` row via `_apply_corrections()`, producing a before/after diff (Task 7.3). It inserts one `AuditLog` row (`action="RESOLVE_INVOICE"`, `details` = target status, dismissed/remaining alerts, and the correction diff) capturing `actor_user_id`/`actor_role` from the JWT context, and commits everything in one transaction. If a correction was made, `_detect_correction_pattern()` checks whether that field has recurred often enough (≥3 times for one vendor, or ≥3 distinct vendors) to suggest a Trainer rule (Task 7.4), returned as `suggested_rule` on the response.

### Gaps
- `[x]` **Gap 419: parking an invoice permanently deleted its alerts** — found by manual QA 2026-09-03, fixed same day. Gap 407 reused the review console's `handleResolve()` for `REVIEW_LATER`/`NEEDS_RESUBMISSION`, but that function was written for *terminal* actions and unconditionally sends `dismissed_alerts: alerts.map(a => a.message)`. `resolve_audit_invoice()` then rewrites `invoice.sa_alerts` with those filtered out and commits — so parking an invoice erased every alert on it. You parked an invoice to review later and came back to one with nothing left to review; you sent an invoice back for resubmission having deleted the record of what was wrong with it. **Fixed** in `app/invoices/review/[id]/page.tsx`: `dismissed_alerts` is omitted, and `setAlerts([])` skipped, for the two parking statuses only — PAID/REJECTED and the no-status Save Correction path (Gap 53/FE 26) keep their existing behaviour exactly. **Backend unchanged** — the contract already supported omitting the field; two tests now pin it. *Observed but out of scope: the Save Correction path also dismisses every alert as a side effect of saving a field correction, which is questionable but pre-existing.*
- `[x]` **Gap 420: a parked invoice could not be returned to the audit queue by any role, including Admin** — found by manual QA 2026-09-03, fixed same day. Two guards both rejected the transition: the Admin-only check on `AUDIT_REQUIRED`, and the "only PAID or REJECTED can be reopened" check. `REVIEW_LATER` is neither, so parking was a **one-way door** — the QA report ("cannot re-click the button") understated it. **Fixed**: the Admin gate moved to after the invoice is loaded, because it now depends on where the invoice is coming *from* — undoing a finalization (PAID/REJECTED → AUDIT_REQUIRED) stays **Admin-only exactly as Gap 193 built it**, while un-parking (REVIEW_LATER/NEEDS_RESUBMISSION → AUDIT_REQUIRED) needs no Admin, since parking was never a decision. A dedicated test asserts the Admin-only reopen was not weakened. `details.previous_status` added to the `AuditLog` payload: both transitions write `action="REOPEN_INVOICE"`, so without it the trail cannot distinguish them — recorded in `details` rather than as a new action string because `services/extraction_quality_rollup.py` consumes exactly `("RESOLVE_INVOICE", "REOPEN_INVOICE")` and a third value would silently vanish from that rollup. FE half in `fe_features_tracker.md`.
- `[x]` **Gap 407: invoice status state machine gains 'Review Later' and 'Needs Resubmission' — two non-terminal deferral states** — opened and built 2026-09-02 from an external defect review ("General — Invoice 'Review Later' & 'Needs Resubmission' States"). `resolve_audit_invoice()`'s status validation now accepts `REVIEW_LATER` and `NEEDS_RESUBMISSION` alongside the existing `PAID`/`REJECTED`/`AUDIT_REQUIRED`.
