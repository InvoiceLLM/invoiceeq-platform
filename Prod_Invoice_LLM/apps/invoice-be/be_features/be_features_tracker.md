- `[x]` **Gap 33: Extraction faithfulness on internally-inconsistent totals** — found Jul 21, 2026, prompt-only mitigation (tightened `grand_total` field description) left a ~1-in-5 residual rate, confirmed live by the Day 1 benchmark run (Jul 22, 2026: 5/30 invoices showed this exact pattern — expected `AUDIT_REQUIRED`, got `COMPLETED`). Prompt tuning alone can't close this — it's asking the LLM not to do something it's stochastically prone to doing. Closed instead with a deterministic, LLM-independent guardrail: `utils/verification_tools.py::verify_grand_total_in_source_text()` checks whether the extracted `grand_total` (in a few plausible printed forms — with/without thousands separator, 0-2 decimals) appears verbatim anywhere in the raw OCR text, called from `agents/extraction_agent.py::verify_node` alongside the existing math checks. Also benefits from the existing retry loop — a failed faithfulness check routes back to `extract` before finally landing on `AUDIT_REQUIRED`.

- `[x]` **Gap 34: RAG chat SQL-lookup non-determinism** — found Jul 22, 2026 via the Day 1 benchmark's RAG chat sample (12/21 pass rate; most failures were "no records found matching the query criteria" for invoices confirmed to exist in the DB). Root cause: `agents/query_agent.py`'s text-to-SQL generation produces a free-form `WHERE invoice_number = '...'` clause per question, with no guarantee of case/whitespace consistency against the stored value. Fixed two ways, both deterministic (no re-prompting): (1) `_normalize_string_equality()` rewrites LLM-generated exact-match filters on OCR/LLM-sourced text columns (`invoice_number`, `vendor_name`, `po_number` — deliberately excludes `status`, which our own code writes and should stay exact) to a case-insensitive, trimmed comparison before execution; (2) `lookup_invoice_by_number_fallback()` — if the generated SQL still finds zero rows and the user's question plainly names a specific invoice (regex-matched), a direct parameterized lookup runs as a safety net, bypassing free-form SQL generation entirely for that case.
- `[x]` **Gap 37: Chat endpoint raw 500 on unhandled query-agent exceptions** — found Jul 22, 2026 via the Day 1 benchmark's RAG chat sample (a genuine `500 Internal Server Error` on a US audit_status question). The SQL/RAG/CHAT routes inside `run_query_agent()` (`agents/query_agent.py`) each already have their own try/except, but two gaps let an exception through anyway: (1) `get_chat_history()`'s DB query itself had no failure guard (only the UUID parsing did) — a transient DB hiccup there propagated straight up; (2) `routers/chat.py::post_chat_message()` called `run_query_agent()` with no try/except at all, so anything unguarded became a raw 500 instead of a graceful chat response. Fixed both: `get_chat_history()` now degrades to an empty history string on failure (missing history is recoverable, not worth failing the whole request over) instead of propagating; the router now catches any exception from `run_query_agent()` and returns a graceful fallback message instead of a raw 500.
- `[x]` **Gap 38: Vendor-lookup questions misrouted to RAG instead of SQL** — found Jul 22, 2026 via a clean benchmark re-run: every failed vendor-name question answered "I can't find this invoice in the provided document extracts," even for invoices confirmed to exist. Root cause: `classify_query()`'s routing prompt described SQL as only for "quantitative checks," so a plain field lookup like "who is the vendor on invoice X" doesn't clearly match either route's description and the LLM inconsistently sent it to RAG (semantic chunk search), which isn't a reliable way to find one specific invoice's exact field value. Fixed by rewriting the routing prompt to explicitly state that SQL covers *any* structured-field lookup (vendor name, dates, PO number, status included), not just quantitative aggregates, reserving RAG for genuinely free-text document content; also added `vendor`/`po number`/`purchase order` to the keyword fallback used when routing classification itself fails.
- `[x]` **Gap 36: Line-item extraction faithfulness (Gap 33's sibling)** — found Jul 22, 2026 while re-running Day 1's exact seed as a regression check for Gap 33. 5 of 6 "expected AUDIT_REQUIRED, got COMPLETED" cases turned out to be a *different* defect than Gap 33: their ground-truth `expected_alert_type` was `line_items_mismatch`/`line_item_calculation_mismatch` (the `subtotal_mismatch`/`rounding_gap` flaw types, which bump one printed line item's amount without touching the printed subtotal), not a grand_total issue at all. Confirmed the same silent-correction behavior as Gap 33, just at the line-item level: e.g. US-20260722-004's extracted line items summed to *exactly* the correct (unflawed) subtotal instead of reflecting the deliberately-wrong printed row amount. Gap 33's fix doesn't cover this — `verify_grand_total_in_source_text()` only checks `grand_total`. Closed with the same pattern applied per line item: `utils/verification_tools.py::verify_line_item_amounts_in_source_text()` checks each line item's extracted `amount` against the raw OCR text, independent of arithmetic, called from `verify_node` alongside the existing checks.
- `[x]` **Gap 39: Chat 500 on SQL-generation column hallucination** — found Jul 22, 2026 via the Day 2 benchmark's RAG chat sample: two audit_status questions returned a real `500 Internal Server Error` (not a grading mismatch). Root cause, confirmed via the backend traceback: `agents/query_agent.py`'s SQL-generation LLM occasionally hallucinates a column that doesn't exist on `Invoice` (`is_audit_required`, `audit_reason` — real audit info lives in `status`/`sa_alerts`) despite the schema prompt listing only real columns. Postgres aborts the whole transaction on the resulting `UndefinedColumn` error; `run_query_agent()`'s except block caught it and built a graceful fallback message, but never called `db_session.rollback()`, leaving the session poisoned so the *next* operation on it — `chat.py::post_chat_message()` saving that very fallback message — failed too, escalating a handled failure into a raw 500. Fixed by adding `db_session.rollback()` to that except block (`agents/query_agent.py`, SQL route). The column-hallucination itself is a separate, lower-severity prompt-quality issue not addressed here — the fix targets the crash, not the occasional wrong-column SQL.

- `[x]` **Gap 46: LLM math auto-correction masking printed vendor flaws** — found Jul 24, 2026 via Day 2 benchmark (seed=2, 3 failures: `us_US-2-003`, `us_US-2-005`, `india_INDIA-2-007`).
