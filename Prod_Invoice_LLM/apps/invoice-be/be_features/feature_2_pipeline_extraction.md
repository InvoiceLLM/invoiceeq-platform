### Pipeline Flow (folder → file → function → functionality)
1. `routers/invoices.py` → `POST /upload`:
   - Fetches the `Tenant` row for `context.tenant_id`; if none exists, **silently auto-provisions one** with a placeholder domain (`domain-{tenant_id}.com`) — an undocumented fallback that bypasses the real domain-based tenant provisioning flow (Website Feature 4 / Clerk gateway). See Task 2.19 / tracker Gap 25.
   - Enforces free-plan limits, then per file: computes a SHA-256 `file_hash` and checks it against existing `Invoice` rows for that tenant. **Exact-hash duplicate detection (Layer 1) is already implemented** — a hash match creates a `status=DUPLICATE` row copying the prior extraction's data and publishes a `DUPLICATE` SSE event immediately, skipping re-processing. Near-duplicate matching (Layer 2 — same `invoice_number` + `vendor_name` with a different file hash, e.g. a rescanned copy) is not implemented. See Task 2.20 / tracker Gap 9.
   - For non-duplicate files: uploads bytes to Blob Storage, inserts `Invoice` row (`status=PROCESSING`), drops message to Azure Storage Queue, returns `batch_id`. (The `run_in_threadpool` callable/args bug that broke this — Task 2.18 / tracker Gap 24 — is resolved.)
2. `queue_worker/handlers.py` → `handle_process_invoice(batch_id, file_path, tenant_id)` — the pipeline orchestrator. Sequence:
   - `_publish_sse_events()` → emits `PROCESSING_OCR` over Redis pub/sub (channel `invoice.update.{batch_id}`), consumed by the FE `EventSource`/polling.
   - `_run_ocr(file_path, settings)` → local `pypdf` text extraction (Ollama/dev) or Azure Document Intelligence `prebuilt-invoice` (prod — Task 2.14 / tracker Gap 15, resolved; returns structured fields, bounding boxes, and per-field confidence, not just raw text).
   - `_publish_sse_events()` → emits `EXTRACTING_DATA`.
   - Looks up a per-vendor layout template: queries `ExtractionTemplate` table by `(tenant_id, vendor_name)`, else falls back to `config/default_templates.json`.
   - Calls `agents/extraction_agent.py::run_extraction_agent()` (first pass with no rules; re-run with template `rules` if a vendor match is found) — see "Extraction Agent Internals" below.
   - Writes extracted fields, `sa_alerts`, and `status` (`COMPLETED` / `AUDIT_REQUIRED`) back onto the `Invoice` row.
   - If `status == COMPLETED`: `_publish_sse_events()` emits `INDEXING`, then `chroma_client.index_invoice_document()` chunks the document and writes vector embeddings for RAG.
   - `_publish_sse_events()` → emits final status (`COMPLETED` / `AUDIT_REQUIRED` / `FAILED`) with the extracted data and alerts payload.
3. `queue_worker/handlers.py` → `handle_import_connector_file(provider, file_id, tenant_id)` — third-party connector variant (Google Drive / Salesforce): downloads the source file, uploads it via `services/storage.py`, creates the `Invoice` row, then synchronously calls `handle_process_invoice()` to re-enter the same flow as step 2.

### Extraction Agent Internals (LangGraph)
`run_extraction_agent()` compiles and runs a 3-node `StateGraph`: `classify → extract → verify`, with a conditional edge looping `verify → extract` on failure (bounded retry). This is current as of Jul 19, 2026 — this section previously described an older 2-node version with no classifier and no retry loop; that was stale for weeks after the work landed. If you're reading this to plan new work, verify against the actual file before trusting prose again.

* `classify_node` → `services/invoice_classifier.py::classify_invoice_complexity()` — keyword/field-presence match (`"gst"`, `"vat"`, `"discount"`, Azure `prebuilt-invoice` field names like `Taxes`/`Discounts`) against the OCR text or structured OCR result, returning `"STANDARD"` or `"COMPLEX"`. **Simpler than the target design**: `Technical_Architecture_Document.md` §7.2 describes "weighted scoring" on layout irregularity/tax structure/line-item count; the actual implementation is a keyword match, not a weighted score.
* `extract_node` — LLM call via `utils/llm.py::get_llm()`, wrapped with `.with_structured_output(InvoiceExtractionSchema)`. Fed OCR text plus base64-encoded page images (`pdf_to_base64_images()`) for multi-modal table/column layout mapping. On `COMPLEX` classification, swaps in a more permissive prompt telling the LLM to extract deeply into the list-shaped fields (`taxes[]`, `discounts[]`, etc.) — **but it's still the same fixed `InvoiceExtractionSchema` structured-output call either way, not a genuinely separate "dynamic schema" path.** On LLM failure or unparseable output, appends an `extraction_failed` alert (the old silent fake-data fallback is gone — see Task 2.13, resolved).
* `verify_node` — **the math validator**, no LLM involved. Calls `utils/verification_tools.py::verify_line_items_math()` (per-line `qty × unit_price × (1−discount) × (1+tax) == amount`, plus `sum(items.amount) == subtotal`) and `verify_totals_math()` (`subtotal + tax − discount == grand_total`). Mismatches are appended to `sa_alerts` as `feedback` and flip `status` to `AUDIT_REQUIRED`.
* `route_after_verification()` — the conditional edge (this is the "Evaluator Router" from the architecture doc, implemented as LangGraph routing logic rather than its own node): if `verify_node` produced alerts and `retry_count < max_retries` (2), routes back to `extract_node` with the alert messages injected into the prompt as "CRITICAL FEEDBACK FROM PREVIOUS EXTRACTION ATTEMPT"; otherwise ends the graph, whatever `verify_node` last set `status` to (`COMPLETED` or `AUDIT_REQUIRED`) stands.

Before either LLM node runs, `check_token_guardrails()` (`utils/token_management.py`) pre-flight-checks estimated prompt tokens against the model's context limit and short-circuits straight to `AUDIT_REQUIRED` with a `token_limit_exceeded` alert if it would overflow.

**Still genuinely missing** (not a documentation staleness issue — verified against the graph definition, these nodes don't exist): the architecture doc's item 5 (**Critic Node** — reviewing `field_confidence` to flag only specific low-confidence fields) and item 6 (**Dynamic QA Node** — generating targeted per-invoice extraction questions on the `COMPLEX` path). `field_confidence` is populated (Task 2.17) but nothing reads it back into the graph; the `COMPLEX` path changes the prompt but not the schema. See Tasks 2.32 and 2.33 below.

### Schema Extensibility Goal (Tasks 2.21, 2.23–2.31)
What we're trying to achieve with this batch of schema work: today, encountering an invoice element the schema doesn't have a field for (a new tax type, a new bank-detail format, an unfamiliar reference number) means it's either silently dropped or mis-stuffed into the wrong field — and fixing it requires a code change and a deploy. These tasks add **list-shaped fields** (`taxes[]`, `references[]`, `tax_ids[]`, etc.) instead of one-off scalar fields, so that once the *shape* exists, recognizing a **new specific value within it** becomes a trainer-taught rule (Global scope, per `feature_10_trainer.md`) instead of a schema migration.

Two different guarantees, depending on the field:
- **Descriptive lists** (`tax_ids[]`, `payment_instructions[]`, `references[]`, `addresses[]`, `compliance_metadata[]`) — nothing computes off these. Once the list exists, a trainer rule can teach recognition of any new country-specific variant (a new tax-ID format, a new e-invoicing compliance code) with **zero code changes, ever again**.
- **Calculation lists** (`taxes[]`, `discounts[]`, `deductions[]`) — a trainer rule can safely teach a *new value* flowing through the list (e.g. "GST" as a `tax_type`), but the arithmetic that consumes the list (Task 2.22) stays fixed in code — a rule should never be able to silently change how totals are calculated.

Net effect once this lands: an Indian GST invoice, a US multi-jurisdiction sales-tax invoice, and a European VAT invoice with reverse-charge notation all extract correctly through the *same* schema, without special-casing any of them in code.

* **P0 Retry-loop content corruption on multi-modal extraction (Resolved Jul 19, 2026)**: `extract_node`'s retry path did `messages[0].content += feedback_msg` where `content` is a list of `{"type": ..., ...}` blocks and `feedback_msg` is a plain string — `list += string` in Python iterates the string character-by-character, appending each character as its own list element instead of concatenating. This corrupted the multi-modal message content array, causing every retry attempt on the Azure/image path to fail with an OpenAI 400 (`Invalid type for 'messages[0].content[N]': expected an object, but got a string instead`) — meaning the retry-with-feedback loop (Task 2.16 / Gap 2) has never actually worked in the multi-modal path since it was built; every math-verification failure just got `extraction_failed`'d on the retry instead of self-correcting. Found via a live test run (one of 4 invoices hit exactly this). Fixed to `messages[0].content.append({"type": "text", "text": feedback_msg})`.
* **P0 OpenAI strict-schema rejection on every extraction call (Resolved Jul 19, 2026)**: `run_extraction_agent()`'s `.with_structured_output(InvoiceExtractionSchema)` call (default `method="json_schema"`, strict mode) failed with `Invalid schema for response_format 'InvoiceExtractionSchema': ... 'additionalProperties' is required to be supplied and to be false` on every single extraction. Root cause, verified empirically: (1) none of the nested models had `model_config = {"extra": "forbid"}`, so Pydantic never emitted `additionalProperties` at all on any of them — not just the ones that triggered the error; and (2) `taxes`, `discounts`, `deductions`, `tax_ids`, `payment_instructions`, `references`, `addresses`, `compliance_metadata` were typed `List[Dict[str, Any]]`, which Pydantic renders as `{"type": "object", "additionalProperties": true}` — structurally incapable of satisfying strict mode no matter what config is set on the parent. Fixed by adding `model_config = {"extra": "forbid"}` to `InvoiceLineItem` and `InvoiceExtractionSchema`, and replacing all 8 `Dict[str, Any]` fields with proper typed nested models (`TaxItem`, `DiscountItem`, `DeductionItem`, `TaxIdItem`, `PaymentInstructionItem`, `ReferenceItem`, `AddressItem`, `ComplianceMetadataItem`), each also `extra="forbid"`. Verified via `model_json_schema()` that the full schema now has zero permissive `additionalProperties` anywhere. (Considered switching to `method="function_calling"` instead — not needed and not done: `langchain_openai` only auto-falls-back to it for Pydantic V1 schemas or legacy `gpt-3`/`gpt-4-`/`gpt-4` model names, neither of which applies to `gpt-4o-mini`; the schema fix keeps the stronger `json_schema` strict-mode guarantee.) The same missing-`extra="forbid"` pattern was also fixed in `query_agent.py`'s `QueryRoutingSchema`/`SQLGenerationSchema` and `trainer_agent.py`'s `ConstraintList` — same root cause, same latent crash risk, see `feature_6_rag.md` / `feature_10_trainer.md`.

* **P0 Structured extraction failure on complex invoices — reasoning-token exhaustion (Resolved Jul 20, 2026)**: `extract_node()`'s `get_llm(max_tokens=4096)` call (`agents/extraction_agent.py` line 182) capped the *combined* reasoning + output token budget for the Azure OpenAI deployment behind `AZURE_OPENAI_DEPLOYMENT_NAME` (a reasoning-capable model, `gpt-5-mini`). On complex invoices requiring more internal reasoning, the model spent its entire 4096-token budget on hidden reasoning tokens (`reasoning_tokens=4096`, `accepted_prediction_tokens=0` in the completion usage) and never emitted the structured JSON output, failing with "Could not parse response content as the length limit was reached." Fixed by raising `max_tokens` to `16384`, giving headroom for both reasoning and output on complex documents.
* **P0 False-positive line-item tax mismatch on invoice-level-only tax (Resolved Jul 20, 2026)**: `verify_line_items_math()` (`utils/verification_tools.py`) added `item.tax_percent`/`item.tax_amount` into a line's expected amount whenever those fields were populated — but `InvoiceLineItem.tax_percent`/`tax_amount` (`agents/extraction_agent.py` lines 34-35) had no instruction limiting them to genuinely per-line-itemized tax, so the extraction model would copy an invoice's single summary-level tax rate onto every line item (there being nowhere else natural to put it). This caused a false `line_item_calculation_mismatch` alert (and incorrect `AUDIT_REQUIRED`) on any invoice where tax is shown once at the invoice level rather than itemized per row — the common case. Confirmed against a real invoice (PrintMax Solutions INV-2026-0002: single line, `Tax (5%)` only in the summary block; `2487.20 × 1.05 = 2611.56` exactly matched the alert's falsely "expected" amount). Fixed two ways: (1) tightened the `tax_percent`/`tax_amount` field descriptions to instruct the model to leave them null unless tax is genuinely itemized per-row; (2) added a defensive guard in `verify_line_items_math()` — if every line item shares an identical `tax_percent` matching the invoice's own effective rate (`tax_amount / subtotal`), it's treated as a copied-down invoice-level rate and the tax step is skipped for that line, rather than trusting the field blindly. Invoices with genuine per-line tax (rates that vary row to row — confirmed safe against a real Indian GST invoice with mixed 18%/12%/0% per-line rates) are unaffected, since the guard only fires when every rate is identical. Regression-tested in `tests/e2e/test_e2e_regional_invoices.py` (`printmax_false_positive`, `vertex_india_gst_complex` fixtures).

* **P0 India/GST math verification false positives (Gap 31, Resolved Jul 21, 2026)**: the stress-test above surfaced four issues in `utils/verification_tools.py`, all now fixed: (1) a flat `0.01` absolute tolerance flagged economically-immaterial rounding differences on large invoices (a real ~13-unit gap on an 80,000-unit line) — added a `REL_TOLERANCE` (0.5%) via a shared `_within_tolerance()` helper, used everywhere the old flat check was; (2) `verify_totals_math()` assumed `subtotal` was always pre-discount, but GST-convention invoices print "Subtotal (Taxable Value)" already net of line discounts — it now tries both the pre-discount and post-discount formulas and only flags a mismatch if grand_total matches neither (invoices without a discount are unaffected, since both formulas collapse to the same value); (3) added a `round_off: Optional[float]` field to `InvoiceExtractionSchema` (`agents/extraction_agent.py`) for the small rounding-adjustment line common on Indian GST invoices, threaded through to `verify_totals_math(round_off=...)`, and tightened the `tax_amount`/`subtotal` field descriptions to instruct the model to sum CGST+SGST into one `tax_amount` value and use the printed subtotal as-is rather than guessing its basis; (4) found only once the fix above was run against the real pipeline (not just unit-tested in isolation): `verify_line_items_math()`'s subtotal-reconciliation check assumed each line's `amount` is pre-tax (matching a pre-tax subtotal directly), but on GST-style invoices `amount` is the line's *post-tax* figure (taxable value + that line's GST) — summing those only reconciles against `subtotal + invoice_tax_amount`, not `subtotal` alone. Now accepts either convention. All four verified together end-to-end via `tests/e2e/test_e2e_regional_invoices.py::vertex_india_gst_complex` (which also required correcting a latent arithmetic inconsistency in the fixture's own test data — its printed subtotal never actually matched its own line items).

* **P0 Extraction faithfulness on internally-inconsistent totals (Gap 33, found Jul 21, 2026, closed Jul 22, 2026)**: while re-verifying the fixtures above, `synthex_deliberate_mismatch` (whose whole purpose is a printed `TOTAL DUE` that deliberately doesn't reconcile with subtotal+tax, to prove the guardrail catches it) intermittently extracted the *arithmetically-corrected* total instead of the printed one — the model's own reasoning trace showed it noticing the discrepancy and "fixing" it rather than transcribing it faithfully, silently defeating the tax-mismatch guardrail. First mitigated (not closed) by tightening `grand_total`'s field description — repeat testing showed 4/4 correct in isolated re-runs vs. 1 failure in the original suite, but the Day 1 benchmark run (Jul 22, 2026) confirmed the residual rate live: 5/30 invoices showed exactly this pattern (expected `AUDIT_REQUIRED`, got `COMPLETED`). Prompt tuning alone can't reach zero here — it's asking the model not to do something it's stochastically prone to doing regardless of instruction. Actually closed with a deterministic guardrail instead: `utils/verification_tools.py::verify_grand_total_in_source_text()` checks whether the extracted `grand_total` (in a few plausible printed forms) appears verbatim anywhere in the raw OCR text, independent of arithmetic — a silently "corrected" total was never actually printed on the document, so it fails this check even though it reconciles perfectly with itself (exactly the blind spot `verify_totals_math` can't cover). Wired into `verify_node` alongside the existing math checks, and benefits from the existing extract→verify retry loop.
