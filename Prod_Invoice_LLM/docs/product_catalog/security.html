Security & compliance

Isolation is structural,
not a configuration option.

Every security property described here is enforced at the architecture layer — not by an application flag that can be misconfigured, overridden, or changed by a vendor update. Cross-tenant reads are not expressible in the system's query layer, not merely prohibited.

Row-Level Database Isolation

A mandatory tenant predicate is applied at the ORM layer on every query. The predicate is injected before the query reaches the database engine — it cannot be bypassed by query construction. A cross-tenant read is not expressible in the system's query model, not merely forbidden by application logic.

Partitioned Vector Indices

Each tenant's document embeddings — the vector representations used for semantic search and SAGE queries — are stored in a physically separate collection with its own namespace. A query from one tenant's session cannot traverse into another tenant's embedding space.

Ephemeral Storage Tokens

Document files are accessed through signed URLs with a 15-minute lifetime. There are no public storage buckets. A URL shared outside the application or captured in a log expires before it can be used — access is always scoped to an authenticated session, not to a long-lived credential.

Asymmetric Authentication

Session tokens use RS256 with JWKS caching and issuer pinning. API keys are stored as PBKDF2-HMAC-SHA256 hashes — the plaintext value is not retained after issuance. A compromised key-store does not yield usable API keys.

Zero Retention for Training

No customer invoice data is used to improve base models. Tenant records, vector indices, and document files are isolated at the storage layer. This is not a contractual commitment sitting on top of a system that could be configured differently — it is the architecture. There is no training data pipeline connected to the production tenant store.

Hard Delete — Complete Purge

When an invoice or document is deleted, it is removed from every store: the relational database, the vector embedding index, and the blob storage file. The delete operation is not a soft flag — it is a hard, atomic multi-store purge. A deleted invoice cannot reappear in chat answers, RAG retrieval, or SAGE queries.

For IT & architecture teams

What InvoiceEQ does not become: your problem.

A finance automation system that requires ongoing IT intervention for rule changes, supplier additions, or entity onboarding is a system that IT ends up owning. InvoiceEQ is designed so that the finance team can operate the system independently:

  • Rule changes — defined and sandboxed through the Trainer UI, not a configuration file or a developer task.
  • New entity onboarding — structural tenant configuration, not a migration or database schema change.
  • Rule rollback — if a promoted rule degrades extraction for a supplier, it is reverted in the same interface that promoted it, without a code deployment.
  • Audit trail — immutable, per-invoice, directly accessible from the audit review interface — no data extract or IT request required for an auditor to pull a specific record.

Cloud deployment on Azure. Regional cloud availability can be discussed. On-premise hardware is not supported.
