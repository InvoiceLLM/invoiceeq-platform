Platform modules

Seven modules. One codebase.
No bolted-on engines.

Every capability is built into the same product — not assembled from third-party point solutions. A correction in EVOLVE propagates to NOVA extraction, SENTINEL verification, and the 3-way match in the same transaction.

NOVA
Vision Intake
99.3% field accuracy < 3.8s median latency 12 document families SHA-256 duplicate gate

What it does

NOVA is the intake layer — the point at which a physical or electronic supplier document becomes a structured data record. It receives files from four channels: email ingest (via configured mailbox), Google Drive / Salesforce sync, direct upload through the web interface, or the REST API. Each file is validated at the byte level before any extraction begins.

How extraction works

NOVA reads documents as documents, not as templates. Azure Document Intelligence provides the visual parse layer, returning page geometry, text runs, and table structures. NOVA then applies a multi-pass LLM extraction step bounded by a strict JSON schema — extracted values are typed (dates in ISO 8601, amounts in exact decimal notation) before they leave NOVA. NOVA never returns a string when the schema calls for a number.

Deduplication before cost

Before any OCR or LLM token is spent, NOVA computes a SHA-256 digest of the file content. An invoice already present in the tenant's database is intercepted in under 5 milliseconds and returned to the operator as a flagged duplicate — no API call to a language model, no extraction cost, no risk of the same invoice reaching the verification step.

What NOVA does not do

NOVA does not decide whether an extracted total is correct. It reads what is printed and passes a structured record to SENTINEL. The boundary is intentional: reading and arithmetic are separated so that each can be tested, audited, and replaced independently.

SENTINEL
Truth Engine
0.00% arithmetic hallucination 10 formal alert codes Hard stop on total mismatch

The core invariant

SENTINEL exists to enforce one rule without exception: if line items plus tax do not equal the stated invoice total, nothing posts to the ledger. There is no confidence threshold, no tolerance band, and no exception path around it. The invariant is implemented in deterministic decimal arithmetic code — not a language model's judgment.

Ten alert codes

When SENTINEL finds a problem, it issues one of ten formal alert codes — each with a specific meaning and a defined routing action. Examples include line_item_calculation_mismatch (the sum of line amounts does not match the stated subtotal), possible_duplicate (same vendor, date, and total but a different invoice number — soft alert, routed to audit queue), and tax anomaly flags. Alert codes are structured, not free-text — they are machine-readable and feed the audit queue, the AI Control Tower, and SAGE's reasoning context.

Why arithmetic is not a language model's job

A language model asked to verify a total generates the most probable sequence of digits. When line items and tax don't reconcile, it produces a figure that makes the arithmetic look right. It never signals uncertainty. SENTINEL replaces this with exact decimal arithmetic in ordinary Python code — a figure it cannot reconstruct stops the invoice, always, regardless of how plausible the mismatch looks.

3-Way Match
Reconciliation Engine
±0.01 tolerance on partial deliveries Vector part-number alignment Retention & holdback aware

Invoice vs. PO vs. goods receipt

A verified invoice is not a paid invoice. Three-way matching checks whether what was billed matches what was ordered (purchase order) and what was actually received (goods receipt / dock receipt). Discrepancies between the three — quantity, unit price, part number — are surfaced before any posting occurs.

Part-number matching with vector similarity

In practice, a supplier's invoice rarely refers to a part number the way the PO does. "Widget A3" and "Wdgt-A3 Rev.2" may refer to the same item — exact-string matching fails; a person would know they match. The reconciliation engine uses vector similarity to align supplier part descriptions to PO line items, tolerating abbreviations, spacing variations, and minor nomenclature differences.

Partial deliveries and retention

Partial shipments and progress billing are handled natively — a billed quantity less than the PO quantity is reconciled against the dock receipt, not flagged as a mismatch. Retention and holdback clauses are recognised as document structure, not as arithmetic failures. Without this, an entire queue of construction or subcontractor invoices becomes exceptions.

EVOLVE
Self-Tuning Rules
0 regressions / 500-doc corpus Rule sandbox before production Vendor-specific and global rules

Learning from corrections without breaking anything

When an auditor corrects an extraction or clears an alert for a specific supplier, EVOLVE observes the correction and proposes a candidate rule — a specific adjustment to how that supplier's documents are read or verified. The rule is proposed, not applied.

The 500-invoice replay requirement

Before any candidate rule goes near production, it is replayed against 500 historical invoices from the relevant supplier corpus. If the rule causes any extraction to regress — produces a worse output than the current system on any document in the replay set — it is rejected. The regression rate across all rules shipped to date is zero.

Scope of rules

Rules operate at three levels: global (applies to all suppliers in the tenant), vendor-specific (applies to a named supplier), and new-vendor bootstrap (defaults used before enough history exists to tune). An operator with no developer access can define and sandbox rules through the Trainer interface — no code, no consulting engagement required. The trainer defines intent; EVOLVE validates safety before promoting.

SAGE
Spend Copilot
Read-only query sandbox 72.2% golden set pass rate SQL drawer with citations

Natural language over the whole invoice history

SAGE allows any authorised user to ask questions of the tenant's full invoice history in plain language: "How much did we pay Cloudflare last month?", "Which suppliers increased unit prices more than 5% in Q3?", "Show me all invoices over $50,000 that went to manual review." SAGE returns a direct answer, the SQL it used to derive it, and citation links to the source invoices.

Dual retrieval path

Aggregation questions ("total spend on vendor X in period Y") route to a generated SQL query against PostgreSQL. Unstructured or policy questions route to semantic vector retrieval over the invoice corpus. Both paths enforce mandatory tenant isolation — a query cannot return data from another tenant's records by construction, not by an application-level flag.

Read-only by design

SAGE has no write access to the invoice database. It cannot approve, reject, flag, or modify any invoice record. This is a structural constraint, not a configuration option — it means SAGE's answer cannot trigger a ledger action by itself, regardless of how the query is phrased.

Autopilot Sync
Scheduling Engine
Google Drive polling Email ingest (global mailbox) Salesforce connector

Intake without a person in the loop

Autopilot Sync removes the human step of collecting, downloading, and uploading invoice files. It polls configured sources on a schedule — a shared Google Drive folder, an inbound email mailbox, or a Salesforce document store — and feeds each discovered file into NOVA automatically. The operator defines the source and schedule; Autopilot handles the rest.

What it does not replace

Autopilot Sync handles collection. It does not handle what happens after a document fails verification or matching — those are SENTINEL and reconciliation engine responsibilities. An invoice that arrives via Autopilot and fails arithmetic verification goes to the same audit queue as one that was uploaded manually.

Outbound AR Pre-Flight
Customer Billing QA
DSO target: 65 → under 25 days Tax splits, PO ref, line maths Contract terms verification

Verify before sending, not after a dispute

The same verification logic that SENTINEL applies to inbound supplier invoices can be applied to the company's own outbound customer invoices before they leave the building. An outbound invoice with a line item arithmetic error reaches the customer, triggers a dispute, and delays payment — a DSO impact that is entirely preventable.

What the pre-flight checks

Line item arithmetic, tax splits against the applicable rate, PO reference matching against the underlying contract, and credit term compliance. An outbound invoice that fails any check is held for correction, not sent. The target DSO improvement (from 65 days to under 25 days) is the downstream result of fewer disputes, not faster chasing.
