# Database Schema Document

This document defines the storage layers for the **Invoice AI SaaS Platform**. The platform uses a hybrid storage model:
1. **Azure Database for PostgreSQL (Flexible Server)**: For structured relational data, transactions, and audit records.
2. **ChromaDB**: For unstructured document text embeddings used in RAG semantic chat, attached-document chat and the support bot.
3. **Redis**: For the async chat job queue, answer/insight caches, per-tenant concurrency limiters, SSE pub/sub and short-lived sessions.

# PART 1: PostgreSQL Relational Database Schema

## Core Schema Rules

1. **Multi-Tenant Isolation**: Every tenant-specific table **MUST** include a `tenant_id` field. All application queries are strictly scoped using this identifier. Two documented exceptions carry a *nullable* `tenant_id` because the row can legitimately belong to no workspace: `supportticket` (anonymous website inquiries) and `dropped_inbound_emails` (mail refused before the sender was matched to a tenant).
2. **Naming Conventions**: Tables declared with `__tablename__` use `snake_case`. Five tables predate that convention and use SQLModel's default lowercase class name with **no underscore**: `tenant`, `invoice`, `tenantconnection`, `chatsession`, `chatmessage` (plus `supportticket`, see §11). The previous version of this document called them `tenants`, `invoices`, `tenant_connections`, `chat_sessions`, `chat_messages` — those names do not exist in the database.
3. **Data Integrity**: Foreign keys are enforced where declared (`users.tenant_id`, `audit_logs.actor_user_id`, `invoice.duplicate_of_invoice_id`, `invoice.source_invoice_id`, `chat_attachments.session_id`, `extraction_template_versions.template_id`, `tenant_email_senders.tenant_id`, `tenant_autopilot_configs.tenant_id`, `tenant_autopilot_logs.tenant_id`, `tenant_workflow_configs.tenant_id`, `sandbox_tenants.tenant_id`, `widget_tokens.tenant_id`). Most other `tenant_id` columns are **indexed but not FK-constrained** — deliberate, so a measurement or log row survives its subject. Cascades are never used; deletes are soft (`deleted_at`, `hidden_at`, `archived_at`, `revoked_at`).
4. **Types as generated by SQLModel**: `UUID` primary keys default to an application-side `uuid4()` (not `gen_random_uuid()`); `str` → `VARCHAR` (unbounded unless `max_length` given); `float` → `FLOAT` (double precision — money columns are **not** `DECIMAL`); `datetime` → naive `TIMESTAMP` populated with `datetime.utcnow()` (there is no `TIMESTAMPTZ` anywhere in the schema); JSON columns use `JSON_VARIANT` = `JSONB` on PostgreSQL, `JSON` on SQLite. No table has a DB-level `CHECK` on a status/role vocabulary except `agent_eval_run` (§17); vocabularies are enforced in routers.
5. **Dev-phase migrations are add-only**: one migration file, one `alembic upgrade head`, no backfill (see Part 3).

# PART 2: ChromaDB Vector Store Collections

ChromaDB is a document-based vector database and does not use a rigid SQL schema. It is organized into **Collections** containing four data layers per record (`id`, `embeddings`, `document`, `metadata`). All collection access goes through `apps/invoice-be/chroma_client.py` (HTTP client to the `ca-chromadb-{env}` container app; `CHROMA_HOST`/`CHROMA_PORT`/`CHROMA_USE_SSL`).

**Tenant isolation is structural, not a metadata filter (Gap 55):** every tenant gets its own collection per document family. Collection names are built by `_tenant_collection_name()`, `_chat_doc_collection_name()` and `_document_collection_name()`. The previous single shared `invoice_chunks` collection filtered by `tenant_id` was migrated by `scripts/migrate_chroma_to_per_tenant.py`.

**Distance space (Gap 244):** every collection is created with `_collection_metadata()` = `{"hnsw:space": "cosine"}`. Chroma pins the space at creation and silently ignores the metadata on an existing collection, so a collection first opened without it is permanently on `l2`; `_collection_space()` reads the live value and `_to_cosine_distance()` normalises. Recovery is drop + re-embed via `scripts/reembed_chroma_collections.py`.

**Embeddings:** `BAAI/bge-m3` (sentence-transformers, `EMBEDDING_MODEL_NAME`), **1024 dimensions**, computed in-process (`get_embeddings()`); `MOCK_EMBEDDINGS=True` in tests. Query embeddings are cached in Redis (`query_embedding:{model}:v1:{sha256}`, 24 h) by `embed_query()`. The model is warmed at process start by `warm_rag_dependencies()` (Gap 278).

## Collection: `invoice_chunks_{tenant_id}`
*Page-per-chunk text of ingested invoices (both flow directions) for the RAG chat route. Written by `index_invoice_document()` from `queue_worker/handlers.py` and `outbound_handlers.py` **only when `should_index_status(status)` is true** — i.e. any status except `NON_INDEXABLE_STATUSES = {UPLOADED, PROCESSING, PROCESSING_OCR, EXTRACTING_DATA, INDEXING, FAILED, DUPLICATE, SKIPPED_DUPLICATE}`; an `AUDIT_REQUIRED` invoice is indexed (Gaps 240/243). Queried by `query_invoice_chunks(tenant_id, query_text, limit=5)`; read whole by `get_all_invoice_chunks()`.*

| Field Name | Data Type | Constraints / Format | Description |
| :--- | :--- | :--- | :--- |
| **`id`** | `String` | `"{invoice_id}_page_{n}"` | One record per non-empty PDF page; upsert-idempotent. |
| **`embeddings`** | `List[Float]` | Exactly **1024** dimensions | `BAAI/bge-m3` vector of `document`. |
| **`document`** | `String` | UTF-8 | `"[Vendor: {vendor} | Document ID: {invoice_id} | Page {n}]\n"` header + the page's extracted text (PyMuPDF). |
| **`metadata`** | `JSON Object` | Enforced at the application layer | See below. |

```json
{
  "tenant_id": "uuid",        // Redundant with the collection name; kept for provenance and cross-checks.
  "invoice_id": "uuid",       // Links back to the `invoice` row; the key `delete_invoice_chunks()` filters on.
  "vendor_name": "Vendor Co", // "Unknown" when the extractor found none.
  "page": 1                   // 1-based page for PDF citation alignment (was `page_number` in the previous version of this doc).
}
```

## Provenance and deletion rules

* **Provenance (Gap 388):** retrieved chunk text is treated as third-party content, not instructions, and every RAG answer is built from and cited against the `invoice_id`/`page` of the chunks it used (`agents/query_agent.py` L2658, L7357; `agents/query_tools.bound_document_pages()` caps pages per document).
* **Soft delete removes vectors (Gap 460, closing Gaps 397-399):** `DELETE /invoices/{id}` and `DELETE /invoices/batches/{batch_id}` call `delete_invoice_chunks()` (and `delete_document_chunks()` for `documents` rows in the batch) **after** the commit; `DELETE /documents/{id}` calls `delete_document_chunks()`. Errors are logged and swallowed so an unreachable Chroma never turns a committed delete into a 500. The earlier Gap 192 policy of keeping chunks for a never-built restore path is gone.
* **Attachment chunks:** `delete_attachment_chunks()` runs from `DELETE /chat/sessions/{id}`, from the TTL sweeper, and from the sandbox sweeper.
* **TTL sweeper (Feature 26 E-7/H8):** `scripts/sweep_chat_attachments.py` (`--dry-run`, `--limit`) deletes rows with `expires_at IS NOT NULL AND expires_at <= now`, chunks first, then blob, then row. Deployed as the `caj-chat-doc-ttl` ACA job (`infra/chat-doc-ttl-job-only.bicep`, cron param `chatDocTtlCron`). `expires_at IS NULL` is **keep**.
* **Tenant-level collection drop:** `delete_tenant_document_collection()` is called only by `scripts/sweep_sandbox_tenants.py` when an expired, unclaimed sandbox tenant is hard-deleted; `reembed_chroma_collections.py` has an orphan sweep for collections whose tenant no longer exists.

# PART 5: Redis (added 2026-09-07)

Redis (`REDIS_URL`; Azure Redis Enterprise on dev) holds no durable data. Everything below is a cache, a queue, a lock or a pub/sub channel and is safe to flush. Extraction work does **not** go through Redis — it uses the Azure Storage Queue `extraction-tasks-queue` (DLQ `extraction-tasks-deadletter-queue`).
