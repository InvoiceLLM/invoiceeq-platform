## Doc dependency graph

`dependency_graph.json` (repo root) maps how the markdown docs in this repo reference each other. Regenerate it with `python dependency_parser.py . -o dependency_graph.json` (uses the fixed parser — do not use any older copy of this script, it has an id-collision bug that silently corrupts edges).

- Each node's `id` is the file's path relative to the repo root (e.g. `Prod_Invoice_LLM/apps/invoice-be/docs/feature_6_rag.md`) — not a bare filename, so ids are unique.
- Each edge `{"source": A, "target": B}` means A references/depends on B's content.

Before opening multiple docs to find related specs:
1. Find the doc's node id — it's just its repo-relative path.
2. Grep `edges` for that id as `source` (what it depends on) or as `target` (what depends on it).
3. Read only those files.

Example: to see what `Prod_Invoice_LLM/apps/invoice-be/docs/be_features_tracker.md` depends on, filter edges where `source` == that path — that's the full feature list it tracks (feature_1_auth.md, feature_2_pipeline_extraction.md, etc.) without opening `docs/` and scanning by hand.

Scope and limits:
- This graph only covers markdown-to-markdown references (feature specs, trackers, `SKILL.md` files, tasklists) detected via `[link](file.md)`, `[[wiki-link]]`, and `Depends on:` text. It does NOT cover code imports between `.py`/`.tsx` files.
- Do not use it for code-change impact analysis (e.g. "what breaks if I edit `agents/query_agent.py`"). Use the code dependency graph below for that — this graph has no signal there.
- A doc with no markdown links/frontmatter deps and nothing linking to it (e.g. most `tests/*/ground_truth_line_items.md`, benchmark reports) will show as a node with no edges. That's expected, not an error in the graph.

## Code dependency graph

Separate from the doc graph above. Each app has its own code-level import graph, generated by `code_dependency_graph.py`:

```
python code_dependency_graph.py Prod_Invoice_LLM/apps/invoice-be --lang py -o be_code_graph.json
python code_dependency_graph.py Prod_Invoice_LLM/apps/invoice-fe --lang ts -o fe_code_graph.json
python code_dependency_graph.py Prod_Invoice_LLM/apps/invoice-website --lang ts -o website_code_graph.json
```

- Each node's `id` is the file's path relative to the scanned app directory (e.g. `agents/query_agent.py`, `components/marketing/Header.tsx`), not the bare filename.
- Each edge `{"source": A, "target": B, "predicate": "IMPORTS"}` means A imports B. One edge per (source, target) file pair, regardless of how many times A imports from B.
- Excludes `node_modules`, `.venv`, build output (`.next` and anything starting with `.next`, e.g. custom dirs like `.next-proxy`), caches, etc. — see `DEFAULT_EXCLUDE_DIRS` in the script.
- Next.js apps resolve the `@/` import alias to the app root by default; pass `--alias @/:some/other/dir` (repeatable) if an app's tsconfig maps it elsewhere.

Use `--impact <path>` to answer "what breaks if I change this file" directly, e.g.:

```
python code_dependency_graph.py Prod_Invoice_LLM/apps/invoice-be --lang py --impact agents/query_agent.py
```

This does a reverse-dependency BFS and prints every file that transitively imports the target, layered by distance — this is the right tool for change-impact questions, not the doc graph.

Known blind spots (static analysis, not runtime tracing):
- Dynamic imports built from a variable (`importlib.import_module(var)`, template-string `import()` paths) aren't resolved.
- FastAPI routes registered by string path and Next.js file-based routing (a page reachable by URL convention, with no explicit import) won't show an edge even though the file is live.
- Imports inside `try/except` are parsed the same as any other import — no special handling either way.
- `alembic/versions/*.py` migration files always show 0 edges — Alembic invokes them by revision id, not by import. Expected, not a bug.

If a graph looks off (implausibly low edge count, a directory of files all showing 0 edges), the most likely causes, in order: (1) a build-output or dependency directory that isn't in the exclude list — check for anything the app builds to that isn't literally named `.next`/`node_modules`/`.venv`; (2) a tsconfig path alias other than `@/` that needs `--alias`; (3) genuinely leaf/presentational files that only import external packages, which is normal, not a bug.
